# Архитектурное решение: AI-инструмент для написания книг

Спасибо за развёрнутые ответы. Картина прояснилась настолько, что можно зафиксировать решения. Ниже — конкретный архитектурный план с обоснованиями, без лишней воды. Где есть развилка — называю выбор и почему.

## 1. Ключевые решения первого уровня

**Стек: TypeScript-монорепо, не Python+React.** Ты явно сказал, что код пишет AI и подгонять под опыт не нужно. Для этого проекта моноязыковой TS даёт три практических выигрыша: (а) AI-агент-кодер держит весь контекст в одном языке и одной системе типов, что уменьшает ошибки на стыках; (б) плагин Obsidian _всё равно_ обязан быть на TypeScript, и моноязык избавляет от перевода типов через границу; (в) экосистема MCP сейчас зрелее в TS, чем в Python. Python проиграл бы только если бы мы делали тяжёлый ML — здесь его нет.

**База данных: SQLite (better-sqlite3) с sqlite-vec.** Ты на одной машине, 3–5 книг, 16 ГБ RAM, не публичный SaaS. Любая сетевая БД (Postgres + Qdrant + Neo4j) — это инфраструктура, которую придётся поднимать, бэкапить, мигрировать. SQLite даёт: транзакции, FTS5 для полнотекстового поиска, sqlite-vec для эмбеддингов в одном файле, нулевую установку, бэкап через копирование файла. Когда (и если) уйдёшь в SaaS — миграция SQLite → Postgres делается за день, потому что Drizzle ORM поддерживает оба диалекта.

**Граф канона — без Neo4j.** Граф будет _проекцией_ на Obsidian-vault через wiki-links, плюс простая таблица отношений в SQLite. Отдельная графовая БД сейчас — overengineering.

**Лицензия InkOS не позволяет копировать код.** Берём идеи и схемы данных, кодовую базу не форкаем. Это решение уже принято в прошлом обсуждении, фиксирую как ограничение.

**Гранулярность агента — через выделение текста.** Это правильная интуиция. Реализация: курсор/выделение в редакторе определяет scope для агента (cursor-style inline AI). Никаких дропдаунов «выбери уровень» — ловим из контекста.

**Двуязычность без паритета в MVP.** Ядро инструмента двуязычно с первого дня (промпты, метаданные, UI), но fatigue-листы, style-guide из референсов и тестовые корпусы делаются для того языка, на котором ты пишешь книгу прямо сейчас. Когда переключаешься на второй — добивается под него. Это снимает половину рутины из MVP.

## 3. Архитектура агентов

Не воспроизвожу 10-агентный пайплайн InkOS — для твоего сценария «диалоговый соавтор с адаптивной гранулярностью» он слишком линейный. Делаю четыре агента + один tool-bag:

| Агент | Что делает | Когда вызывается | Модель в MVP |
|---|---|---|---|
| **Brief Agent** | Из свободного намерения автора («хочу главу про предательство в пещере») делает структурированный бриф: цель сцены, конфликт, POV, эмоциональная цель, длина | На входе любого workflow | Claude Sonnet 4.5 (через Claude Pro/API) |
| **Planner Agent** | Из брифа выдаёт N вариантов плана (beat-sheet или scene-list, в зависимости от уровня) | После брифа | Claude Sonnet 4.5 |
| **Writer Agent** | Из выбранного плана пишет прозу. Получает на вход: план + relevant canon + style fingerprint + список fatigue-слов | После одобрения плана | Claude Opus 4.7 (платим больше за главное) |
| **Auditor Agent** | Проверяет драфт: канон (есть ли противоречия), стиль (близость к references), AI-tells (fatigue-слова, ритм), пейсинг | После Writer'а или по запросу | Claude Sonnet 4.5 (дешёвый и достаточно умный для проверки) |

Tool-bag (доступен агентам через Anthropic tool-use):

```
get_canon(book_id, query)         → relevant entities/scenes via hybrid retrieval
get_character(name)               → персонаж с историей
get_recent_chapters(book_id, n)   → последние N глав для контекста
get_style_fingerprint(profile_id) → структурированный style guide
list_fatigue_words(profile_id, lang) → слова под запретом
search_references(query, lang)    → поиск в корпусе референс-книг
write_canon_delta(book_id, delta) → атомарное обновление канона (Zod-валидируется)
log_decision(reason, refs)        → decision log
```

Tools — реальные TypeScript-функции, которые модель вызывает через native tool-use Anthropic. Никакого ReAct и парсинга строк.

## 4. Workflow: уточнённый сценарий работы

Твоё MVP-описание принимаю как основу, но добавляю явные уровни и branching, потому что иначе одобрение каждого слова превратит работу в ад. Предлагаю вот такой каскад с вариантами выхода в любой точке:

```
[Уровень 1: Концепция книги]
  Автор: премиса в свободной форме
    ↓
  Brief Agent → структурированный бриф книги (жанр, аудитория, тема, тон)
    ↓
  Planner Agent → 2–3 варианта high-level outline (синопсис + основные арки)
    ↓
  Автор: выбирает / редактирует / regenerate
    ↓ commit как Book v1

[Уровень 2: Арка]  ←─── при необходимости можно зайти и сюда сразу
  Автор выбирает арку или просит сгенерировать список
    ↓
  Planner Agent → структура арки (3-act / save-the-cat / freytag по выбору) + scene-list
    ↓
  Автор: выбирает / редактирует
    ↓ commit как Arc v1

[Уровень 3: Глава]
  Автор пишет намерение главы или выбирает scene из арки
    ↓
  Brief Agent → бриф главы
    ↓
  Planner Agent → 2–3 варианта beat-sheet главы
    ↓
  Автор: выбирает
    ↓
  Writer Agent → проза (стримом в редактор)
    ↓
  Auditor Agent (опционально) → отчёт по канону / стилю / AI-tells
    ↓
  Автор: правит вручную или просит частичный regenerate
    ↓ commit как Chapter version N

[Уровень 4: Inline]
  Автор пишет в редакторе. Выделяет фразу/абзац или ставит курсор.
  Команда «продолжить» / «переписать» / «сократить» / «усилить эмоцию»
    ↓
  Writer Agent с урезанным контекстом (только окружение + relevant canon)
    ↓
  Suggestion-blob появляется рядом → accept / reject / regenerate
```

Branching живёт на каждом уровне: каждый node в этом дереве — это сущность с версиями. Любую версию можно «форкнуть» — создать альтернативу и развивать параллельно. Это превращается в схему данных (раздел 5).

В MVP реализуем уровни 1, 3 и 4. Уровень 2 (арка) можно отложить — между книгой и главой пишется руками без агента.

## 5. Схема данных (только важное)

```typescript
// Дерево «концептуальных» сущностей с версионированием
Book        { id, title, language, premise, current_version_id, ... }
Arc         { id, book_id, parent_arc_id?, title, ... }
Chapter     { id, book_id, arc_id?, order, title, current_version_id, status }
Scene       { id, chapter_id, order, title, ... }

// Версии — иммутабельные снимки
Version     { id, entity_type, entity_id, parent_version_id?,
              content_md, prompt_used, agent, model, created_at, branch_label? }
// branch_label = null → mainline; "alt-darker", "alt-faster" → ветки

// Канон (Story Bible)
Character   { id, book_id, canonical_name, profile_json, ... }
Location    { id, book_id, name, profile_json }
Item        { id, book_id, name, profile_json }
Hook        { id, book_id, seed_scene_id, status, // open|mentioned|resolved|deferred
              description, expected_resolution_chapter? }
CharacterKnowledge { id, character_id, fact, learned_in_scene_id }  // что персонаж знает
Relationship { id, from_id, to_id, type, tension, evolution_log_json }

// Память (для retrieval)
Embedding   { id, source_type, source_id, language, embedding(BLOB), text_chunk }
SceneSummary { id, scene_id, summary, key_facts_json, embedding_id }

// Решения и аудит
Decision    { id, book_id, type, summary, refs_json, agent_votes_json, version_id }
AuditReport { id, version_id, dimensions_json, severity_summary, fixed }

// Стиль
StyleProfile { id, name, language, fingerprint_json, fatigue_words_json,
               reference_corpus_ids[], created_at }
```

Зачем `parent_version_id` и `branch_label` — это git-style branching, который ты просил. UI показывает дерево версий для главы, любую можно сделать «текущей», ветки можно мерджить (полуручной merge с показом diff).

`profile_json` для персонажей и пр. — это вложенный документ по нашей более ранней схеме (want/need/lie/voice/relationships). Не разворачиваем в плоские таблицы — Zod-валидация на чтении и записи решает.

## 6. Память и retrieval — вместо PageIndex

PageIndex сейчас не беру. Причина не в том, что он плох — концептуально он интересен (древовидная навигация по документам), — а в том, что добавляет внешнюю зависимость, для которой нет реальной ниши в твоей задаче. Книга _уже_ имеет иерархию (book → arc → chapter → scene), и эта иерархия живёт в SQLite как foreign keys. Использовать PageIndex поверх — означает построить ещё один индексер, держать его в синхронизации, и за это получить ту же навигацию, которую даёт SELECT с JOIN.

Что делаю вместо:

**Гибридный retrieval = sqlite-vec + FTS5 + структурный фильтр.**

- На каждое изменение сцены/главы/канон-сущности фоновый job:
  1. чанкует текст (по абзацам, окно 400–800 токенов с overlap 100),
  2. генерит эмбеддинги через `voyage-3` (дёшево) или `text-embedding-3-small`,
  3. кладёт в `embeddings` с метаданными `(book_id, type, language, ref_id)`.
- На запрос Writer'а / Auditor'а:
  - семантический поиск через sqlite-vec (top-K по cosine),
  - параллельно FTS5 по словоформам (особенно важно для имён, мест),
  - Reciprocal Rank Fusion двух списков,
  - **обязательный структурный фильтр**: «только эта книга, только до текущей главы, только этот POV-персонаж» — иначе агент будет «знать» спойлеры из будущих глав.

Это и есть «PageIndex-like иерархическая навигация» — но реализованная штатно, без отдельного фреймворка.

К референс-книгам (Сандерсон, Толкин и т.д.) — отдельный индекс, помеченный `is_reference=true`, с другим режимом цитирования: **никогда не вставлять отрывки в проза-выход**, только использовать для stylistic fingerprinting и retrieval-augmented prompting под особыми инструкциями. Это снимает риск буквального плагиата (см. раздел 11).

## 7. Стиль референс-авторов — реалистичный план

Жёсткая правда: на твоём бюджете и без GPU **настоящего fine-tune не будет**. Anthropic не предоставляет fine-tuning в Claude Pro. OpenAI fine-tune доступен, но лочит на их модели и стоит денег при инференсе. Реалистичный путь — это **stylistic fingerprinting + few-shot retrieval + system-prompt injection**, и это правда работает на 60–70% от ожидания «как тот автор».

Конкретный пайплайн:

**Фаза A: одноразовая обработка корпуса (раз на книгу-референс)**
1. Парсим epub/fb2/pdf/txt → plain text + main matter (отбрасываем оглавление, копирайт).
2. Детектируем язык, разбиваем на сцены/главы по эвристикам (главы по `Глава N` / `Chapter N`, сцены по двойным переводам строки).
3. Запускаем **Style Extractor Agent** (Claude Sonnet, один прогон на ~50 случайных сцен из корпуса). Он возвращает структурированный JSON: распределение длин предложений, плотность диалога/описания/действия, любимые тропы, частотные синтаксические конструкции, типичный ритм абзаца, подход к scene-opening и scene-closing, обращение со временем (présent / past), частота метафор и их «семья».
4. Параллельно — **fatigue word detection**: топ-N часто используемых лексем для жанра (берём из общего корпуса того же жанра, не из автора), помечаем как «избегать».
5. Сохраняем `StyleProfile` (один на автора-референса, или комбинированный «Сандерсон + Пехов с уклоном в первого»).

**Фаза B: использование при генерации**
1. Writer получает в system-prompt:
   - сжатый style fingerprint (≈500–800 токенов, не full JSON),
   - 2–4 короткие few-shot цитаты из корпуса референса через retrieval (с пометкой «ориентир по голосу, не копировать»),
   - **жёсткое правило в инструкциях**: запрет на буквальные совпадения >7 слов с любым chunk'ом из reference-корпуса.
2. Auditor получает тот же fingerprint и проверяет драфт: BERTScore-подобное сравнение, плюс LLM-judge с rubric «насколько похоже на стиль X».

Что это _не_ даёт: «Сандерсон-уровня магической системы». Style-fingerprint — про голос и ритм, не про сюжетную инженерию. Сюжет всё равно идёт от твоего брифа.

Что делать с шестью авторами одновременно: профили хранятся отдельно, **на проект выбирается один или микс** (например, «70% Пехов + 30% Кинг»). Микс — это weighted prompt: в system-prompt берётся пропорциональное число few-shot от каждого, и инструкция «доминирующий голос — Пехов, эмоциональная интенсивность — Кинг».

Технологии для этого: ничего экзотического. Anthropic SDK + sqlite-vec + один Style Extractor промпт. Ноль ML-зависимостей.

## 8. Obsidian: file-watcher или MCP — ответ

Ты спросил, что дешевле по токенам. Прямой ответ: **ни то, ни другое само по себе ничего не экономит**. Токены тратятся на _инжект данных в промпт_, а не на способ их получения. Сравним по реальной стоимости:

| Подход | Когда и сколько данных уходит в LLM | Сложность реализации |
|---|---|---|
| File-watcher без индексирования (наивно) | Весь vault в каждый промпт → дорого | Низкая |
| File-watcher + парсинг в БД + retrieval | Только релевантные куски в промпт → **дёшево** | Средняя |
| MCP-сервер | Агент через tool-use запрашивает только то, что нужно → **дёшево**, но + N round-trips | Средняя-высокая |

Рекомендация: **file-watcher + парсинг в БД** на MVP. Vault — это просто папка markdown. На каждое изменение `.md` файла chokidar триггерит парсер: вытаскиваем frontmatter, wiki-links, теги — кладём в `Character`/`Location`/`Hook` таблицы в SQLite. Отдельный MCP не нужен, потому что vault = view-слой, а не источник правды (ты сам сказал — БД источник).

Когда добавлять MCP: если/когда захочешь работать с vault'ом из Claude Code напрямую — поднимешь MCP-сервер _поверх_ той же БД, без изменения архитектуры.

Vault структурируем _мы_, раз ты не структурировал. Конвенция:

```
vaults/<book-slug>/
├── 00 Meta/
│   ├── Premise.md
│   └── Style Profile.md
├── 10 Characters/
│   └── <Имя>.md           # frontmatter: type=character, want, need, lie, scars
├── 20 Locations/
├── 30 Items/
├── 40 Arcs/
│   └── <Название>.md      # содержит [[wiki-links]] на сцены
├── 50 Chapters/
│   └── 01 - <Название>.md # тело главы; всегда projection from DB
└── 90 Decisions/
    └── 2026-05-07-fake-artifact.md  # decision log
```

Главы в vault'е — read-only проекции из БД (генерируются на каждый коммит версии). Если ты правишь главу руками в Obsidian — file-watcher это видит, и UI показывает «vault и БД разошлись, мерджить?». Без автомерджа: или БД → vault, или vault → БД, по явному выбору.

## 9. Humanizer и AI-tell detection — что я предлагаю

Репозиторий `blader/humanizer` я в этой сессии не открывал (rate-limit на github). На уровне README такие инструменты обычно делают одно из: (а) обходят AI-детекторы через перефраз, (б) добавляют «человечности» через намеренные нарушения паттернов LLM. Для художественной прозы (а) — мимо, потому что детекторы AI-текста для литературы ненадёжны, и борьба с ними — тупик. (б) — полезно.

## 13. Риски и допущения

**Допущения, которые ты должен подтвердить или опровергнуть:**
1. Ты пишешь _преимущественно_ либо на русском, либо на английском (не 50/50). Если 50/50 — двуязычный паритет придётся в MVP, бюджет времени растёт на ~30%.
2. «3–5 книг параллельно» — это **активная разработка** или включая «лежит в архиве, иногда смотрю»? Если активная разработка пяти одновременно — это нагрузка, которую один автор-человек обычно не тянет; MVP я калибрую под 1–2 активные книги.
3. Готов пожертвовать веб-доступом «из любого места» в MVP ради скорости (в моём плане инструмент работает локально, БД-файл на диске). Это твой явный ответ, фиксирую.

**Риски, на которые закладываюсь:**

1. **Плагиат из референс-корпуса.** Snippet-injection в few-shot создаёт ненулевой риск буквальных совпадений. Контрмера: жёсткое правило в промпте + post-generation n-gram check (≥7 слов matched → Auditor флаг + автоматический rewrite).
2. **Style-profile «слипает» голоса разных авторов в среднестатистический LLM-голос.** Контрмера: Style Extractor запускается с явной инструкцией «выделить отличия от среднего, а не общие черты», и микс делается через _чередование_ few-shot, а не через смешивание fingerprint'ов.
3. **AI-кодинг ломает мигрант версии.** При сложной схеме версионирования AI-агент может «потерять» поле. Контрмера: Drizzle migrations в git, schema-snapshot тесты в CI.
4. **AGPL-блок в случае открытия SaaS.** Мы не используем код InkOS. Используем идеи и схемы — это безопасно. Но `humanizer` и `PageIndex` — проверим лицензии _до_ интеграции, не после.
5. **Bus-factor 1 + AI-кодинг** = код есть, но «никто не помнит, как это работает». Контрмера: ADR-документы в `/docs/adr/` после каждого этапа (3–5 строк: что решили, почему, какая альтернатива отвергнута). Это AI тоже умеет.

## Принятые поправки + развёрнутые ответы

Решения 1–5 фиксирую: TS, TipTap, MVP только русский, workflow принят, первый референс — Пехов. Ниже отвечаю на пункты 6–8 и переписываю архитектуру под 7+ агентов и LangGraph.

### Q6. Почему я отверг LangGraph и почему теперь меняю позицию

Честный ответ почему отверг: для 4 агентов с почти линейным flow (Brief → Plan → Write → Audit) свой код на ~300 строк с типизированными контрактами читается яснее, чем декларативный граф. LangGraph даёт абстракции (state, edges, checkpointer, interrupts), которые в простом случае пустуют, а ошибки в промптах прячутся за слоем фреймворка. Для AI-кодинга это плохо: AI легче пишет прямой код, чем графовые DSL.

Почему меняю позицию сейчас: ты возвращаешь 7+ агентов с параллельной фазой критики и self-repair loop'ом. Здесь LangGraph.js окупается на трёх вещах:

1. **Параллельные ноды и conditional edges из коробки.** Самописный fan-out на 4 критика + агрегатор + условный переход в self-repair — это тот код, который AI пишет с ошибками race conditions. LangGraph декларативно: задаёшь edges, фреймворк гарантирует семантику.
2. **Checkpointer.** На каждой ноде state сохраняется в SQLite. Это бесплатно даёт нам time-travel и branching по умолчанию — то, что ты явно просил. Не нужно отдельно изобретать систему версий пайплайна, она уже встроена.
3. **`interrupt()` для HITL.** Native приостановка пайплайна на одобрении автора, с возможностью продолжить из чекпойнта.

Цена: дополнительная зависимость, чуть менее прозрачные стек-трейсы при ошибках, и LangGraph.js всё ещё немного отстаёт от Python-версии по фичам (например, durable execution слабее). Для нашей задачи это терпимо.

**Решение:** используем LangGraph.js + Anthropic SDK напрямую внутри нод. То есть LangGraph — оркестратор, но LLM-вызовы делаются прямо через `@anthropic-ai/sdk` с native tool-use, без обёрток LangChain. Это даёт максимум контроля и минимум абстракций между нами и моделью.

### Q6 (продолжение). Как пайплайн в принципе может меняться

Список реалистичных изменений, под которые надо закладывать гибкость уже сейчас:

- **Вставка нового критика** (Sensitivity Reader, Continuity Checker, Genre-Fit) — добавляется как ещё одна параллельная нода в фазе критики, без переписывания соседей.
- **Backward-edit от Foreshadowing Agent.** Когда в главе 22 появляется твист, агент должен предложить правки в главы 3, 7, 12. Это нелинейный edge — пайплайн «ходит» в прошлые главы и создаёт под-задачи. В LangGraph это subgraph; в самописе быстро превращается в макароны.
- **Разные пайплайны под тип сцены.** Экшен-сцена не нуждается в Dialogue Agent, диалоговая — наоборот в Scene Director'е. Conditional routing по типу сцены на старте.
- **Series Planner overlay.** Когда появится вторая книга, Plot Agent на каждой главе должен консультироваться с series-level арками. Это вертикальная композиция: пайплайн книги «оборачивается» в пайплайн серии.
- **Voting между критиками.** Сейчас агрегация — простое объединение замечаний. Когда два критика противоречат друг другу (Editor: «слишком длинно», Reader-Experience: «нужна сцена для эмоционального якоря»), должен быть арбитражный шаг.
- **HITL-gate в любой точке.** Сейчас одобрение только перед коммитом. По мере усложнения захочется паузы перед Writer, перед самовосстановлением и т.д.
- **Замена модели на агента.** Например, Style Agent с Sonnet → локальный fine-tune на стиле Пехова, когда такая модель появится.
- **Branching пайплайнов.** Запустить две разные генерации главы параллельно с разными настройками («жёстче» / «мягче»), сравнить, выбрать.

Все эти изменения в LangGraph — добавление нод и edges. В самописе — рефакторинг state machine.

```
                          [Plot Agent]
                         /    |    \
                        v1   v2    v3      ← variants по настройке
                              |
                          USER PICKS
                              |
                              v
                     ┌──── prepare context ────┐
                     |                          |
              [Lore Agent]              [Character Agent]
                     |                          |
                     └──────── bundle ──────────┘
                              |
                              v
                       [Writer Agent]   ← с style fingerprint Пехова
                              |
                              v
                          DRAFT
                              |
                ┌───────┬─────┴─────┬───────────┐
                v       v           v           v
          [Canon       [Style    [Editor    [Reader-
           Guard]      Agent]    Agent]     Experience]
                |        |          |            |
                └────────┴──── aggregate ────────┘
                              |
                         blocking? ──── no ──→ DRAFT OK
                              |
                             yes
                              v
                      [Self-repair loop]
                       (max 3 iterations)
                       Writer rewrites with
                       prioritized critiques
                              |
                              v
                          revised draft
                              |
                              v
                    HITL gate (interrupt)
                              |
                       USER: accept / edit / branch
                              |
                              v
                        commit Version
                        update canon
                        decision log
```

Каждый блок в этой схеме — это нода LangGraph. Пунктирные edges (HITL, self-repair) — conditional. Checkpointer SQLite сохраняет state на каждом шаге, что даёт нам:

- **Retry с любой точки** без перезапуска предыдущих шагов (если Writer упал — запускаем только Writer, не Plot).
- **Branching пайплайна**: сделать копию state в нужной точке, запустить альтернативную ветвь.
- **Time-travel в UI**: «откатить план главы на версию выбора, попробовать другой вариант».

## Финальные решения по объёму MVP

Зафиксировано после ответов на вопросы 1–2.

**1. Полная фаза критики с первого MVP — никаких stub'ов.**
Все 4 критика (Canon Guard, Style, Editor, Reader-Experience) реализуются сразу. Бюджет MVP — 6–8 недель по плану выше, без срезов. Причина выбора: stub-критики откладывают самую ценную часть системы (защиту канона + контроль AI-tells), и их потом всё равно пришлось бы переделывать после первой реальной главы. Лучше один раз построить полный контур.

**2. Self-repair loop — вариант B: ручной запуск после показа сырого драфта.**

Поток:
```
Writer → DRAFT → 4 критика параллельно → aggregate → отчёт критиков
   ↓
USER видит:
  • полный сырой драфт от Writer
  • список замечаний (severity: blocking / suggestion / nit)
  • кнопка "Запустить self-repair" (если есть blocking или suggestion)
  • кнопка "Принять как есть"
  • кнопка "Редактировать вручную"
   ↓
если USER нажал self-repair:
  → Writer переписывает с приоритетом по blocking → новый драфт + новые отчёты
  → max 3 итерации, каждая по решению пользователя
```

Причина выбора (B):
- Видишь сырой выход модели — калибруешь интуицию по Writer'у на ранних главах.
- Не платишь токены за repair, который не нужен.
- Self-repair часто «перебарщивает» (LLM-критики флагуют то, что не блокер). Ручной gate отсеивает шум.
- Когда наберётся статистика «90% repair-предложений принимаются» — переключим на A одной настройкой.
