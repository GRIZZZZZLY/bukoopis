# Jev (TypeSafe AI) в book-forge: можно ли и как

Дата: 2026-09-19. Источник: docs.typesafe.ai (introduction, models, api, state, primitives, patterns, cookbooks/rerank).

## Вердикт

Использовать можно, но только для узкого класса задач и только после проверки на русском тексте. Jev не генерирует текст, поэтому он не заменит ни одного из наших генеративных агентов (писатель, ревизор, критики, извлекатели, классификатор материала). Он заменяет или добавляет **решения**: выбор из списка, оценку по шкале, ответ да/нет с калиброванной вероятностью. У нас таких решений мало, но одно уже спроектировано именно как «LLM-судья» и выключено из-за цены — реранкер. С него и начинать.

## Что такое Jev

- Модель «System One»: принимает `state` (строка, JSON-объект или массив текстов) и карту типизированных вопросов, отвечает структурой. Три примитива: `choice` (вариант из списка + вероятности + `confidence`), `score` (позиция на шкале из 2–10 описанных уровней + вероятности + `confidence`), `noul` (вероятность «да», 0–1).
- Все вопросы одного запроса считаются параллельно и независимо против одного `state`. Добавление вопросов почти не меняет время ответа. Типичный запрос ≈ 100 мс.
- Один эндпоинт `POST https://api.typesafe.ai/v1/systemone`, ключ `TYPESAFE_API_KEY`. JS/TS SDK `@typesafe-ai/sdk` (Node 20+, ESM и CJS, типы ответов выводятся из вопросов). Можно и просто `fetch`.
- Модель `jev-1.13.0` (алиас `jev-latest`). Цена $0.042 за миллион входных токенов, выход бесплатно. Контекст: 64k токенов на запрос целиком, 32k на `state` плюс самый длинный вопрос. Лимиты 250k токенов/с и 1200 запросов/мин, меняются без предупреждения.
- Только текст. Не пишет ответов, не объясняет, не цитирует.

## Главный риск: русский язык

Документация прямо говорит: основной язык обучения английский, остальные «обрабатываются, но не так хорошо; проверьте на своём контенте прежде чем полагаться, и смотрите на `confidence` при маршрутизации». У нас всё на русском. Это не запрет, но любое внедрение начинается с эвала на нашем тексте, а не с кода в основной ветке.

## Где Jev подходит, где нет

| Место в проекте | Сегодня | Что мог бы делать Jev | Подходит |
|---|---|---|---|
| `rerank.ts` + агент `reranker` | LLM-судья, выключен (`RETRIEVAL_RERANK=1`), потому что дорог | `score` или `noul` «кандидат отвечает на запрос» по каждому кандидату; кукбук по реранку ровно об этом | **Да, первый кандидат** |
| `canon_guard` / `critic_canon` | Sonnet по прямому API, ищет противоречия канону | Предфильтр: `state` = глава, по одному `noul` на каждый активный факт «глава противоречит факту F». Дальше LLM-критик смотрит только помеченные и даёт цитаты | Да, гибрид; критику всё равно нужны цитаты, их Jev не даёт |
| Дедупликация фактов и событий (`normalizeEventData`) | Ключ по нормализованному смыслу | `noul` «эти две записи об одном и том же» для пар с похожими сущностями | Да, дёшево, маленький `state` |
| `resolveEntity` на тёзках | Возвращает `null`, факт не пришивается никому | `choice` «к какому из героев относится упоминание» с `confidence`-порогом; ниже порога — прежний `null` | Да, но только как второй шаг после точного совпадения |
| `material_classifier` (интейк) | Один генеративный вызов на файл: режет на фрагменты и назначает цель | Только назначение цели фрагменту (`choice` из `INTAKE_TARGETS`). Резку на смысловые фрагменты Jev не сделает — она генеративная | Частично; выигрыш не очевиден, пока резка остаётся у LLM |
| Критики стиля/читателя, `measureStructuralTells` | Регэкспы плюс LLM с цитатами | Мог бы дать калиброванный `score` «машинности» по сцене как ещё одну метрику | Спорно: философия слоя «измерено, не угадано», а это опять угадывание, пусть и калиброванное |
| Соответствие главы плану | Нет | `score` по каждому полю намерения главы (`goal`, `conflict`, `stakes`, `hook`): «насколько глава это выполняет» — показать автору рядом с главой | Да, новая фича для «прозрачности», не для MVP |
| `selectVoiceSamples` | Детерминированный отбор, порядок стабилен ради кэша префикса | Ранжирование по релевантности сцене | **Нет**: любая недетерминированность ломает кэш промпта Писателя |
| Писатель, ревизор, генераторы питчей, извлекатели, сводки | Генерация | — | **Нет**, Jev не генерирует |

## Рекомендация: пилот на реранкере

Почему именно он: уже спроектирован как судья, уже выключен по цене, уже имеет passthrough-фолбэк (`items.slice(0, topK)`), поэтому провал пилота ничего не ломает. Цена вопроса: пул из 30 кандидатов по ~300 токенов плюс запрос ≈ 10–15k токенов (кириллица токенизируется тяжелее английского) → около $0.0006 за вызов против ~$0.05 у Sonnet. Это позволяет включить реранк по умолчанию, чего с LLM не сделали.

Шаги:

1. **Эвал до кода.** 20–30 реальных запросов из своей книги, для каждого — пул кандидатов из `hybridSearch` и разметка руками «релевантно/нет». Прогнать через Playground или скрипт на `fetch`. Смотреть top-1/top-5 против текущего RRF-порядка и распределение `confidence`. Если на русском не лучше RRF — остановиться, записать результат сюда.
2. **Клиент.** Один файл `packages/llm/src/clients/jev.ts` на `fetch` (около 30 строк: POST, Bearer, ретрай на 429/529 с backoff). SDK `@typesafe-ai/sdk` ставить, когда появится второе место вызова. Ключ — `TYPESAFE_API_KEY` в `apps/server/.env`.
3. **Замена внутри `rerankByRelevance`.** `state` = `{ query, candidates: [{id, text}] }`, вопросы — по одному `noul` на кандидата: «Кандидат N отвечает на запрос». Сортировка по `noul`, `topK`. Флаг оставить тем же `RETRIEVAL_RERANK`, контракт агента `reranker` не трогать до успеха пилота, потом удалить.
4. **Учёт.** Строка `jev-1.13.0` в `pricing.ts` (вход $0.042/Mtok, выход 0), drift-guard тест по `MODEL_IDS` подскажет, где ещё. `usageLogger` — вызов записывать как платный, `usage.input_tokens` приходит в ответе.
5. **Второй шаг при успехе:** предфильтр противоречий канону перед `canon_guard` (пункт 2 таблицы). Он снимает с Sonnet большую часть работы и напрямую бьёт по критерию «долгая память».

## Что это стоит в будущем

- Второй внешний поставщик и второй ключ. Ломает формулировку «единственное облако — LLM API» из брифа; для однопользовательского локального инструмента это приемлемо, но надо записать в решения.
- Лимиты и цены «меняются без предупреждения». Фолбэк на passthrough обязателен везде, где Jev стоит на пути генерации.
- Нет самостоятельного развёртывания: без сети реранк молча деградирует до RRF. Для реранка это норма, для чего-либо на пути «принято/не принято» — нет.
- Правило проекта «модельный ответ не считается доверенным потому, что он правильной формы» действует и здесь: калибровка заявлена по группам предсказаний, отдельный ответ может быть неверным. Любое решение Jev, влияющее на канон, идёт через порог `confidence` и остаётся предложением автору, не фактом.

## Чего не делать

- Не заменять Jev'ом ни одного генеративного агента.
- Не ставить его в путь сборки кэшируемого префикса промпта.
- Не включать в основную ветку до эвала на русском тексте.
