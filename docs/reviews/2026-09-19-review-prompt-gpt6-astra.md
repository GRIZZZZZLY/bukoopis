## Задача

Провести независимое ревью репозитория **book-forge** и написать отчёт: реальные дефекты с доказательствами, архитектурные риски и честная оценка проекта как инструмента для написания романов. Результат работы — один документ отчёта. Исходники проекта в рамках этого ревью не меняются: исправления описываются словами, а не патчами.

## Что перед тобой

book-forge — локальный однопользовательский инструмент для написания романов с помощью LLM, русскоязычный MVP. Один автор, один компьютер, единственное облако — API языковой модели.

Ставка продукта — конвейер с человеком в контуре: модель предлагает варианты, автор выбирает, правит и принимает, принятое становится каноном и подаётся следующим генерациям. Второй столп — слоистая память: книга на 30+ глав не разваливает контекст, потому что промпт собирается из ограниченных слоёв (скользящее окно последних глав, сводки по рубежам, временны́е факты канона, эпизодические заметки, события персонажей на границе сцены, гибридный поиск по прошлым главам).

Правило, которое проходит через все подсистемы: **ничего не утверждается без автора**. Импорт материалов, быстрый сбор черновиков, генерация главы, правка — всё приходит в статусе «на рассмотрении» и ждёт явного принятия.

Стек: pnpm-монорепо, Node 22+, ESM, TypeScript strict с `noUncheckedIndexedAccess`. Сервер — Hono и `better-sqlite3` (один файл, WAL, прямой SQL; Drizzle только как описание схемы, миграции рукописные). Веб — React 18, Vite 6, Tailwind v4, TipTap. LLM — Anthropic API напрямую и второй бэкенд через `claude-agent-sdk`; каждый агент со структурным выводом регистрирует контракт с zod-схемами и вызывается через `dispatchStructured`. Около 1300 vitest-тестов, LLM в них замокан.

```
apps/server      Hono API, вся бизнес-логика, SQLite (src/routes, src/utils, drizzle/)
apps/web         React SPA
packages/shared  zod-схемы, типы, инварианты studio, prose-diff, prose-rules
packages/agents  контракты агентов: writer, reviser, plot, critics, inline, extractors, intake
packages/llm     dispatcher, router агент→бэкенд, retry, structured
packages/retrieval, packages/style-engine
docs/            CLAUDE.md в корне, adr/, superpowers/specs/, migrations.md, prose-tells-baseline.md
```

## Что стоит знать заранее

- `CLAUDE.md` в корне — самый свежий документ. Там записаны решения последних фаз и их причины. В коде много комментариев «намеренно», «сознательно», `ponytail:` с названным потолком. Спорить с такими решениями можно и нужно, если есть аргумент; повторять их как находку — нет.
- Остальные документы (`docs/project-brief-for-llm.md`, `docs/architecture-overview.md`) старше и местами расходятся с кодом, например в названиях моделей. Код — источник истины; расхождения — отдельный раздел отчёта.
- У проекта есть история молчаливых потерь: экран говорил «память актуальна», когда разбор был пропущен, отброшен или сделан старой версией конвейера. Такие места ищи первыми.
- Две разные границы сцены, которые нельзя путать: `beforeChapterOrder` в `chapter-retrieval.ts` — включающая, вызывающий передаёт `order - 1`; `excludeFromChapterOrder` в `character-events.ts` — исключающая. Любое попадание содержимого главы ≥ N в подготовку главы N — критический дефект.
- `order_index` глав разрежённый, шаг 10. Расстояние между главами считается только через `chapterPositionLookup`.
- `dispatchStructured` не принимает сигнал отмены: реестры отмены в памяти проверяются между шагами, идущий вызов прервать нечем. Подписочный бэкенд не сообщает `stop_reason`; предел длины на нём доезжает через `CLAUDE_CODE_MAX_OUTPUT_TOKENS`.
- Схемы, по которым строится инструмент модели, идут через `z.toJSONSchema`: `.transform` внутри них ломает генерацию.
- Решено и вне рамок, это не пробелы: мультипользовательская авторизация, мобильная вёрстка (ниже 768px — не баг), второй язык, ветвление сюжета в интерфейсе, ESLint/Prettier/Husky/Docker/CI, интеграция с Obsidian/MCP, облачная синхронизация.

## Что можно делать без вопросов

Это локальный инструмент, продакшена нет. `pnpm install`, `pnpm typecheck`, `pnpm test` — запускай сразу. Сервер можно поднять с `DB_PATH`, указывающим на пустой или временный файл; `data/db.sqlite` может содержать реальную книгу автора — работай с копией. Тесты не требуют API-ключа; живого ключа у тебя нет, обходись без живых вызовов.

## Что считается готовым

Отчёт готов, когда:

- прочитаны все маршруты в `apps/server/src/routes` и все модули в `apps/server/src/utils`, `packages/shared`, `packages/llm`; на фронте — страницы и панели, которые держат состояние;
- `pnpm typecheck` и `pnpm test` выполнены и результат записан, либо прямо сказано, почему не удалось;
- каждая находка содержит файл и строку, сценарий отказа (какое состояние или ввод дают какой неверный результат) и уверенность: `подтверждено` или `вероятно`;
- расхождения документации и кода перечислены;
- дана оценка как инструмента для писателя по критериям ниже;
- перечислено, что осталось непроверенным и почему.

Доводи до этого состояния, не возвращаясь за подтверждением после первого прохода. Если отчёт не влезает в один ответ, продолжай в следующем без вопросов.

## Что важно в дефектах

Критический уровень: потеря данных автора; утечка будущих глав в прошлое; что-то утверждается без автора; результат записывается после отмены. Высокий: неверный результат для автора, зависание, молчаливая деградация. Средний: неудобство, скрытая деградация без последствий для текста. Низкий: остальное.

Зоны, где дефекты находили раньше и стоит ожидать ещё: атомарность транзакций и проверка `expectedRevision` с ответом 409; три SSE-раннера с реестрами в памяти при рестарте сервера и закрытой вкладке; жизненный цикл `prose_proposals` и частичное принятие через LCS по абзацам; интейк — резка по 40 000 символов, `.docx` через jszip, ключ кэша по тексту; локальное состояние форм, не следящее за сервером; рендереры, доверяющие форме payload без схемы; N+1 в SQL и содержимое стабильного префикса промпта.

## Оценка как инструмента для писателя

Отвечай как продуктовый эксперт, который сравнивал реальные инструменты: Sudowrite, Novelcrafter, NovelAI, Scrivener с плагинами, сырой чат с моделью. Оценивай по тому, что код реально делает, а не по описанию. По каждому критерию — оценка 1–10, обоснование с отсылкой к коду и один шаг, который поднял бы оценку на балл.

1. Человек в контуре: где правило «без автора» держится, где нарушается, где автора заставляют кликать без смысла.
2. Долгая память: переживёт ли книга 30, 60, 100 глав без противоречий и раздувания промпта; что сломается первым.
3. Индивидуальность персонажей: голос, знание на границе сцены, направленные отношения с качествами, образцы речи — доходит ли это до промпта или остаётся структурой данных.
4. Качество прозы и слой «де-AI»: измерение штампов, архитектурный лист, калибровка критиков, правила Ревизора — сдвигает ли текст или остаётся благим пожеланием в промпте.
5. Путь от идеи до первой главы: шаги, экраны, решения; где автор потеряется.
6. Импорт готовой работы: автор с «библией» на 50 000 символов и десятью главами — сколько действий до рабочего состояния и что потеряется.
7. Прозрачность: видит ли автор, что модель знает о книге в момент генерации, что потерялось, за что он платит.
8. Надёжность многочасовой сессии с обрывами сети, рестартами и закрытыми вкладками.
9. Стоимость владения: долларов на главу и на книгу по коду (генерация, критики, правка, извлекатели, сводки); где срезать без потери качества.
10. Архитектурный запас: что станет тормозом при росте глав, сущностей и агентов.

Заверши сводной оценкой по 10-балльной шкале и одним абзацем: кому инструмент подходит сегодня, кому нет, и что одно надо сделать, чтобы это изменилось.

## Отчёт

По-русски; имена файлов, функций, таблиц и событий — как в коде. Начни с резюме на десять строк: общее впечатление, три главных риска, главная сильная сторона. Дальше — дефекты по убыванию серьёзности с развёрнутым разбором критических и высоких, расхождения документации и кода, архитектурные паттерны (а не единичные строки), оценка как инструмента, десять первых шагов в порядке приоритета, непроверенное. Форма внутри разделов — на твоё усмотрение; важна проверяемость каждого утверждения читателем с кодом под рукой.
