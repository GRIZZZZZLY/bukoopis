# BOOKOPIS (book-forge) — бриф проекта для обсуждения с LLM

> Самодостаточное описание идеи и архитектуры. Составлено 2026-07-31 по состоянию main.
> Контекст: single-user инструмент, работает локально, русскоязычный MVP готов и протестирован.

## 1. Идея

**book-forge** — локальный AI-ассистированный инструмент для написания романов. Один пользователь (автор), один компьютер, никакого облака кроме LLM API. Продукт ведёт автора от замысла до готовой книги в EPUB: структурированная проработка мира → посерийный план → генерация глав с критикой → экспорт.

Ключевая ставка — не «кнопка напиши книгу», а **конвейер с человеком в контуре**: LLM предлагает варианты, автор выбирает/правит/принимает, принятое становится каноном, канон автоматически подаётся следующим генерациям. Второй столп — **слоистая память**: книга на 30+ глав не разваливает контекст, потому что промпт собирается из ограниченных слоёв, а не из «всего текста подряд».

Язык произведений — русский. UI — «тёплая библиотека»: атмосфера кабинета писателя (полка книг, рукопись, доска сюжета с красными нитями).

## 2. Стек

- Монорепо pnpm workspaces, Node 22 LTS, ESM only, TypeScript strict (`noUncheckedIndexedAccess`).
- Backend: **Hono** (порт 3001), **better-sqlite3** (один файл, WAL), опционально `sqlite-vec` для векторного поиска + FTS5. Drizzle — только как описание схемы; runtime — прямой SQL. Миграции — рукописный plain SQL + journal.
- Frontend: React 18, Vite 6, Tailwind v4 (CSS-first, дизайн-токены в `:root`), TipTap (редактор рукописи), react-router-dom 7. shadcn/ui как source-in-repo.
- LLM: Anthropic API (`claude-sonnet-4-6` для сюжета/критики, `claude-opus-4-7` для писателя) + альтернативный бэкенд через `claude-agent-sdk` (OAuth-подписка Claude Code). Эмбеддинги — локальный ONNX.
  - Актуальные цены за 1M токенов (вход/выход, справочник на 2026-06-24): Opus 5 и Opus 4.7 — $5/$25; Sonnet 5 — $3/$15 (вводная $2/$10 до 2026-08-31); Sonnet 4.6 — $3/$15; Haiku 4.5 — $1/$5; Fable 5 — $10/$50. Чтение из prompt-кеша ≈0.1× входа, запись 1.25× (TTL 5 мин) или 2× (1 ч). Batch API — −50%.
  - **Opus 5 стоит столько же, сколько используемый сейчас Opus 4.7** — апгрейд Writer'а не увеличивает цену. Ломающие изменения при переходе: мышление включено по умолчанию (нужен запас `max_tokens`), `thinking: disabled` допустим только при effort ≤ `high`, минимальный кешируемый префикс падает до 512 токенов.
- Тесты: vitest, ~300+ по workspace (LLM-вызовы замоканы). Всё зелёное.

## 3. Структура workspace

```
apps/server      — Hono API, вся бизнес-логика, SQLite
apps/web         — React SPA
packages/shared  — Zod-схемы, типы, инварианты studio
packages/agents  — контракты всех LLM-агентов (промпты + схемы I/O)
packages/llm     — диспетчер, роутер бэкендов, retry, стриминг
packages/retrieval    — hybrid search (FTS5 + вектора)
packages/style-engine — стилевые профили
```

Импорты между пакетами — только через `workspace:*` и `exports`, не в `src/` соседа.

## 4. LLM-слой (центральная абстракция)

Каждый структурный агент регистрирует **AgentStructuredContract**: input-схема (Zod), output-схема, системный промпт. Вызов — `dispatchStructured({agentName, payload, model})`. Диспетчер валидирует вход/выход и маршрутизирует на один из двух бэкендов:

- **api** — прямой Anthropic API (биллинг по токенам);
- **subscription** — spawn Claude Code CLI через `claude-agent-sdk` с вырезанным `ANTHROPIC_API_KEY` → работает на OAuth-креды подписки; структурный вывод через mcp_submit_tool.

Роутер (`DEFAULT_AGENT_BACKEND`) распределяет по агентам: писатель/редактор/аспекты/память → subscription; сюжет/критики/canon-guard → api. Переопределение через env `LLM_AGENT_BACKEND_MAP`. Bootstrap при старте сервера регистрирует все контракты и падает, если какой-то агент без контракта (drift-guard тест дублирует проверку).

**Агенты (~22):** plot_outline, plot_chapter_plan, writer, editor, inline, summarizer, metaSummarize, critic_canon, critic_style, critic_editor, critic_reader, canon_guard, lore, character, style_extractor, concept_refiner, aspect_playbook, aspect_variants, aspect_refine, aspect_entity_variants, canon_fact_extractor, episodic_note_extractor, reranker.

## 5. Studio — 7-этапный конвейер построения книги

Маршрут `/books/:id/studio`. Этапы: **концепт → мир → лор → персонажи → предметы → сюжет → главы**. Гибкий dashboard без жёстких гейтов, но с soft-warnings («лор не начат после мира» и т.п.).

- **Концепт**: реестр жанров (16, с иерархией) + тонов (9, с матрицей несовместимости); «пазл посылки» — LLM генерирует 2–3 варианта на поле (протагонист → конфликт → ставки → логлайн), принятые поля накапливаются в контекст следующего.
- **Мир/Лор** (markdown): LLM предлагает 5–9 «аспектов» (география, магия, фракции…), по каждому — 2–3 варианта текста с учётом уже принятых; refine порождает вариант-потомок, родитель помечается superseded.
- **Персонажи/Предметы** (entity_set): варианты — наборы именованных сущностей с профилями; принятые **материализуются** в канонические таблицы `characters`/`items`.
- **Сюжет/Главы**: plot-агенты видят весь принятый контекст через `loadStudioContext` (концепт + принятые аспекты мира/лора + материализованный канон).

Состояние — JSON в `books.studio_state` с оптимистичной блокировкой (revision, HTTP 409 на конфликт) и 7 жёсткими инвариантами перед каждым persist. Аспектный движок двухслойный: `StageAdapter<TPayload>` (рендер/схема payload) + оркестраторы `AspectRunner`/`EntityStageRunner` — новые типы этапов добавляются адаптером.

## 6. Память (решает проблему длинной книги)

Экстракторы работают не «fire-and-forget», а через **устойчивую очередь** `memory_jobs` (ADR 0002): задания (`index`/`summary`/`facts`/`notes`/`rollup`) ставятся в очередь атомарно вместе с коммитом версии главы, привязаны к `chapter_version_id`, имеют статусы `pending|running|retry|done|error|obsolete`, до 5 попыток. Фоновый воркер (`startMemoryWorker`) обрабатывает их; stateful-задания (`facts`, `notes`) забираются строго в порядке глав и блокируются незакрытыми заданиями более ранних глав. Результат сначала стейджится, затем проходит гейт активации (`memory-activation.ts`): если `chapters.current_version_id` уже не тот, задание становится `obsolete` и его вывод **не применяется** — правка принятой главы не оставляет устаревших фактов.

Провенанс частичный: у фактов есть `source_version_id`, `confidence`, `assertion_mode` и явный supersede; поля `source_kind` (manual/llm/imported) и `review_status` отсутствуют — граница «канон vs машинная интерпретация» пока задаётся confidence, а не типом источника.

Слои контекста генерации главы:

1. **Rolling window** — последние 3 главы (краткие саммари) дословно + ОДИН мета-роллап всего более старого. Промпт ограничен при любой длине книги.
2. **Retrieval** — hybrid search (FTS5 + вектора) по чанкам предыдущих глав, top-k в промпт Writer/Plot; фильтр `beforeChapterOrder` исключает самоутечку.
3. **Темпоральные факты канона** — `book_facts` со сроком действия (`valid_from/valid_to_chapter`, supersession): «герой не умеет колдовать в гл. 3, умеет в гл. 12» — Writer и Canon-Guard видят факты, актуальные именно на текущей главе.
4. **Эпизодические заметки** — `book_notes` (нити, форшадоуинг, арки, тайны) с векторным поиском; открытые нити подаются Plot и критику-читателю. Визуализируются на «доске сюжета» (стикеры на пробке, красная нить от появления до закрытия).
5. **Reranker** (LLM-judge над пулом retrieval+notes) — выключен по умолчанию (`RETRIEVAL_RERANK=1`).
6. **POV-знание** (ADR 0003, слайс 3b): таблица `character_knowledge` + `pov-context.ts` — что персонаж узнал к текущей главе (`learned_in_chapter_id`). Writer'у разрешено озвучивать в мыслях POV только это, авторское знание в голову персонажа не попадает. Плюс `entity-resolve.ts` — сущности с ID и алиасами (слайс 2) и `context-compiler.ts` — сборка секций контекста с бюджетом токенов (слайс 3).

Закрыто 2026-08-01:
- **Дословный хвост предыдущей главы** (`loadPreviousChapterTail`) — последние ~6000 символов, обрезанные по границе абзаца, подаются Writer'у как отдельный слой контекста (priority 2) с инструкцией продолжать интонацию и доигрывать незавершённое действие.
- **Предупреждение о лаге памяти** (`pendingEarlierMemoryChapters`) — генерация главы N по-прежнему не блокируется, но `GET /api/chapters/:id` отдаёт `memory.pendingEarlierChapters`, и ChapterPage показывает баннер «Память глав #… ещё обновляется: если начать писать сейчас, эти главы не попадут в контекст».
- **Провенанс фактов** (миграция 0018) — `source_kind` (llm_extraction | manual | accepted_studio | imported_document) и `review_status` (unreviewed | confirmed | disputed | rejected) отдельно от `assertion_mode`. `loadActiveFacts` не отдаёт `rejected`.

Оставшиеся пробелы памяти: нет «контракта главы» (must_happen / must_not_happen / expected_revelations / разрешённые изменения канона), поэтому Canon-Guard не отличает запланированное изменение канона от ошибки; нет UI для ревью фактов (колонки есть, менять `review_status` пока можно только через SQL); нет детерминированного контроля повторов (частотные наречия, одинаковые речевые теги, повторяющиеся n-граммы) в подаче critic_style.

## 7. Цикл главы

План главы (plot_chapter_plan) → Writer (Opus, стриминг, версионируется) → саммари/факты/заметки извлекаются в фон → критика по 4 осям (канон/стиль/редактура/читатель) + canon_guard → автор правит вручную или через inline-агента → следующая глава. Стилевые профили (style_extractor) подмешиваются в Writer. Экспорт: Markdown + EPUB.
