# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`book-forge` — single-user, local-first AI-assisted novel-writing tool. Russian-language MVP. pnpm workspaces monorepo, Node 22+ (проверено на 24), ESM only, TypeScript strict (`noUncheckedIndexedAccess`).

**Node и `better-sqlite3`.** Единственная нативная зависимость — `better-sqlite3`. Её авторы публикуют готовые сборки под каждую ABI, и версия 11.x кончалась на ABI 127 (Node 22): на Node 24 установка срывалась в node-gyp, которому нужен Visual Studio, и база не открывалась вовсе. Поэтому зависимость поднята до `^12.11.1` — 12.x заявляет Node 20–26 и публикует сборку под ABI 137. Понижать Node не нужно. Если `pnpm install` всё же уходит в node-gyp, значит `prebuild-install` не достучался до GitHub; сборку можно положить руками в `node_modules/.pnpm/better-sqlite3@<версия>/node_modules/better-sqlite3/build/Release/`, взяв её из релиза `better-sqlite3-v<версия>-node-v<ABI>-win32-x64.tar.gz` (ABI — `node -p process.versions.modules`).

## Commands

Run from repo root unless noted.

```bash
pnpm install
pnpm migrate                # apply SQLite migrations to data/db.sqlite
pnpm dev                    # server :3001 + web :5173 in parallel
pnpm dev:server             # server only
pnpm dev:web                # web only
pnpm typecheck              # tsc across all packages
pnpm test                   # vitest across all packages
pnpm build
```

Single test file:

```bash
pnpm --filter @book-forge/server test -- src/routes/__tests__/studio.test.ts
pnpm --filter @book-forge/web test -- src/components/studio/concept/__tests__/ConceptForm.test.tsx
```

Migrations are **hand-written plain SQL** — this is the official process, not a stopgap. Drizzle-kit snapshots are out of sync since 0008 and `drizzle:generate` emits a wrong diff; do NOT use it. The runtime migrator reads `meta/_journal.json` + `.sql` files (not snapshots). Scaffold a new one with `pnpm --filter @book-forge/server drizzle:new <name>` (creates the `.sql` + appends the journal entry), edit the SQL, update `schema.ts` for docs/types, then `pnpm migrate`. `pnpm migrate` auto-backs-up the DB (`VACUUM INTO` → `data/backups/`, last 10). Full process: [docs/migrations.md](docs/migrations.md).

Env: `apps/server/.env` holds `ANTHROPIC_API_KEY` (gitignored). Server reads `PORT`, `DB_PATH`. Web reads `VITE_API_BASE_URL`.

## Architecture

Workspace layout: `apps/{server,web}` + `packages/{shared,agents,llm,retrieval,style-engine}`. Inter-package imports go through `workspace:*` and the package `exports` field — never reach into `src/` of another package.

**Server** ([apps/server/src/app.ts](apps/server/src/app.ts)): Hono app with one db connection (`better-sqlite3`, WAL, optional `sqlite-vec`). Routes mounted under `/api`: `health`, `books`, `chapters`, `plot`, `retrieval`, `import-export`, `entities`, `critique`, `inline`, `style`, `usage`, `canon-extraction`, `studio`. Bootstrap in [apps/server/src/index.ts](apps/server/src/index.ts) calls `registerAllAgentContracts()` + `registerStyleExtractorContract()` + `assertAllStructuredAgentsHaveContracts()` BEFORE `createApp()` so `dispatchStructured` can resolve every agent.

**LLM dispatcher** ([packages/llm](packages/llm/src/)): every structured-output agent registers an `AgentStructuredContract` (input schema, output schema, system prompt, MCP spec). `dispatchStructured({ agentName, payload, model })` routes to Anthropic API or `claude-agent-sdk` mcp_submit_tool backend. Two backends: subscription (default, mcp_submit_tool) and direct API. Adding an agent = add to `AGENT_NAMES`/`STRUCTURED_AGENT_NAMES` ([packages/llm/src/types.ts](packages/llm/src/types.ts)) + write contract in `packages/agents/src/...` + register in [packages/agents/src/bootstrap.ts](packages/agents/src/bootstrap.ts).

**Studio workflow** (`/books/:id/studio`): 7-stage pipeline replacing the old title→outline→chapter flow. Stages = concept, world, lore, characters, items, plot, chapters. World/lore use markdown payloads; characters/items use `entity_set` and materialize into canon tables (`characters`, `items`).

**Замысел (2026-09-04, фаза 1 конвейера):** книга создаётся из одного поля `idea` (`POST /books` принимает `idea` без `title`, название по умолчанию «Новая книга»). Этап concept = `IdeaIntake` → `PitchBoard` (агент `pitch_generator`, 3–5 питчей, дописываются к `concept.pitches`; `pitch_blender` собирает один питч из выбранных строк) → `ConceptCard` (утверждённый замысел, `concept_refiner` даёт другие формулировки строки). Поле задумки в `ConceptStage` — локальное состояние, но оно синхронизируется с пропом `concept.idea`: приём материалов заполняет замысел на сервере, и без синхронизации форма продолжала показывать пустоту до перезагрузки страницы. Набранный и не сохранённый текст при этом не затирается. Готовность этапа = `concept.lockedAt` (`POST /concept/lock` копирует питч в premise/genre/tone/hook и ставит название книги; `/unlock` снимает). `genre`/`tone` — свободные строки из питча; каталога жанров и пикеров нет, старые массивы `genres/tones` сворачиваются в `normalizeConcept` при чтении. Подписи строк только из `PITCH_FIELD_LABELS` — слова «логлайн», «протагонист», «ставки», «премиса» в интерфейсе не появляются. Спецификация всей перестройки: `docs/superpowers/specs/2026-09-04-author-pipeline-redesign.md`.

**Приём материала (2026-09-05, фаза 2 конвейера):** `POST /books/:id/intake` принимает пачку файлов (`.md/.markdown/.txt` текстом, `.docx` как `contentBase64` — распаковывается [`docxToPlainText`](apps/server/src/utils/docx.ts) через jszip; эта зависимость уже была в `apps/server/package.json` до фазы 2, новой не заводили). На каждый файл — последовательно, один за другим — идёт один вызов агента `material_classifier` (`maxTokens: 32000`, до 40 фрагментов на файл), который режет его на фрагменты и приписывает каждому цель из `INTAKE_TARGETS` ([packages/shared/src/intake.ts](packages/shared/src/intake.ts)). Файл длиннее `MAX_INTAKE_FILE_CHARS` (40 000 символов) не отвергается, а режется на части по границам абзацев — [`splitIntakeFile`](apps/server/src/utils/intake-split.ts); авторская «библия» одним документом на 48 000 символов и есть типичный материал интейка, отказ по размеру оставлял автора ни с чем. Дальше часть живёт самостоятельной единицей разбора: своё имя (`файл.docx (часть 2 из 4)`) в строке прогресса, в `failures` и в ключе дочитывания, свой вызов классификатора. Файл, влезающий целиком, проходит сплиттер неизменным — вместе с именем, а значит и со своим ключом в журнале, так что старые записи `processedFiles` продолжают совпадать. Абзац длиннее предела рубится по символам: потерять его целиком хуже. Отказ по файлу (нечитаемый .docx, падение классификатора) по-прежнему ложится в `failures`, а не 400 на весь запрос, и остальной пакет приземляется. Причину отказа `IntakeSummary` печатает рядом с именем — раньше выбрасывала, и «Не удалось разобрать: X» не говорило автору ничего. Приземление — `landFragments` ([utils/intake-landing.ts](apps/server/src/utils/intake-landing.ts)): мир/лор/план ложатся аспектами `payloadKind: "markdown"`, персонажи и предметы — `entity_set` с кандидатами `proposed`, готовые главы идут через `insertChapters` из import-export, задумка попадает в `concept.idea` только если её там ещё нет — из поля `bookIdea` в ответе классификатора, а если его нет, то из **первого фрагмента с target `concept`** (обрезанного до 8000 символов). Второй источник обязателен: цель `concept` есть в каталоге целей и описана в системном промпте, так что модель с равным основанием возвращает замысел фрагментом, а `landFragments` аспекты такой цели выбрасывает — замысел исчезал молча, автор видел «ошибки нет», пустое поле и предупреждения про незаданный жанр. Аспектом фрагмент по-прежнему не становится: этапа под него нет. Сам `runIntake` пишет ход разбора в консоль под тегом `[intake]` (единицы и ключ, каждый вызов классификатора с таймингом и раскладкой по целям, ответ из журнала, итог, и отдельной строкой — решение по замыслу с причиной). Это единственное место, где видны его молчаливые решения. **Ничего не утверждается автоматически:** аспект приходит `status: "reviewing"`, `source: "import"`, без `finalPayload`, с одним вариантом статуса `generated` — то самое состояние, из которого `AspectRunner` принимает одной кнопкой. Повторное перетаскивание того же набора возвращает прошлый ответ по ключу в событии `import_merge`; ключ (`intakeRequestKey`) считается не по сырому телу запроса и не по фрагментам классификатора, а по уже расшифрованному тексту файлов — после `docxToPlainText`, до вызова агента. Миграции нет: `source: "import"` и тип события `import_merge` лежали в zod-схеме с Studio Phase A задолго до этой фазы; отдельный `payloadKind` под импорт не понадобился — `import_candidate` в `PAYLOAD_KINDS` так и остался неиспользуемым, интейк переиспользует существующие `markdown`/`entity_set`. Фрагмент, нацеленный на персонажей/предметы, но без единой разобранной сущности, уходит на `lore` markdown-аспектом (сводка называет `lore`, а не то, куда целился классификатор): этап сущностей рисует только карточки, и строка в `entity_set`-рендерере роняла всё приложение — граница ошибок одна, в `main.tsx`. `EntityStageRunner` теперь ещё и пропускает любой payload через схему адаптера и вместо падения показывает сообщение. Журналируется (и, значит, кешируется) только прогон, в котором что-то легло — `landed.length > 0 || chapters.length > 0 || ideaSet`; прогон, где всё упало, повторяем. Папку `DropZone` обходит через `webkitGetAsEntry()` — сами `dataTransfer.files` при перетаскивании папки дают одну бесполезную запись; вызывать `webkitGetAsEntry` надо синхронно, до первого `await`. Чтение файлов в `IntakePanel` — по одному, а не `Promise.all`: непрочитанные встают в `failures` рядом с отказами сервера. Оркестрация — один раннер, `runIntake` ([utils/intake-run.ts](apps/server/src/utils/intake-run.ts)), и оба маршрута зовут его: `POST /books/:id/intake` — синхронно, один JSON-ответ прежней формы (`summary/ideaSet/chapters/failures/revision`), удобен для скриптов; `POST /books/:id/intake-stream` зовёт тот же раннер через SSE и стримит `begin` (несёт `requestKey`), на каждый файл пару событий `file` (`started`, затем `done` или `failed`), а в конце — `done` (та же форма плюс `cancelled`) или `error`. Классификатор зовётся со **своим пределом ожидания** — `timeoutMs: 600_000` в `runMaterialClassifier` (поле `timeoutMs` у `dispatchStructured`, работает на обоих бэкендах). Общий `LLM_TIMEOUT_MS` (120 с) рассчитан на короткий структурный ответ, а классификатор переносит текст автора дословно и на куске в 40 000 символов пишет минутами: предел рубил его посреди работы, причём subscription-бэкенд сообщал это как «Claude Code process aborted by user» — самая большая часть документа не разбиралась никогда, а сообщение уводило искать, кто нажал отмену. Обрыв по собственному таймеру теперь и называется таймаутом ([mcp-submit-tool.ts](packages/llm/src/clients/mcp-submit-tool.ts), `catch` вокруг цикла сообщений). Таймаут остаётся retryable, так что худший случай на зависшем бэкенде — 4 попытки по 10 минут. Разбор живёт в процессе сервера, а не в SSE-соединении: обновление или закрытие вкладки его не прерывает, но и не показывает — поток видит только та вкладка, которая его открыла. Поэтому реестр `intakeInFlight` (в памяти, ключ — книга) держит снимок прогона (`requestKey`, `total`, `startedAt`, строки файлов в том же виде, что рисует экран), а `GET /books/:id/intake/inflight` его отдаёт (404 = «ничего не идёт», штатный ответ). `IntakePanel` при монтировании спрашивает его и, если разбор идёт, подхватывает: рисует тот же прогресс, опрашивает раз в 2 с, кнопка «Остановить» работает по ключу с сервера; исчезновение прогона из реестра = «Разбор завершён» + `onIntake()`. Итог подхваченного прогона вкладке не достаётся — его получила та, что открывала поток. Часы «идёт N мин» в `IntakeProgress` — не украшение: один вызов классификатора на большой части молчит минутами, и без бегущего времени экран неотличим от зависшего. По той же причине поток раз в 20 с шлёт событие `ping` (клиент игнорирует неизвестные события) — молчащее соединение вправе закрыть кто угодно по дороге. Остановка — `POST /books/:id/intake/cancel` с `requestKey` из `begin`; проверяет его реестр в памяти процесса ([utils/intake-cancel.ts](apps/server/src/utils/intake-cancel.ts)), ключ — пара «книга + requestKey», а не одна книга, чтобы отмена не задела чужой разбор той же книги. Реестр смотрят между файлами: `runIntake` проверяет флаг перед началом каждого следующего файла и, если он поднят, останавливается там — **прервать уже идущий вызов классификатора нечем**, `dispatchStructured` не принимает сигнал отмены. Поэтому отменённый прогон ничего не откатывает: то, что фрагменты уже успели приземлить, остаётся, прогон журналируется как обычно и отвечает обычным `done` с `cancelled: true`, а не событием `error`.

**Предложения прозы (2026-09-05, этап 1 индивидуальности персонажей):** генерация главы (`POST /chapters/:id/write`) и правка (`POST /chapter-versions/:id/repair`) больше не коммитят результат. Обе создают строку в `prose_proposals` **до первого токена** (`status: "streaming"`) и шлют её id событием `proposal`; по завершении кандидат получает `ready` или `incomplete`. `incomplete` — это не ошибка, а честный ответ: `stop_reason` читается только на прямом API, бэкенд подписки его не сообщает вовсе, поэтому `isConfirmedCompletion(null)` — `false`, и такой кандидат принимается только осознанно. Версия создаётся единственным местом — `acceptProposal` ([utils/prose-proposals.ts](apps/server/src/utils/prose-proposals.ts)): одна транзакция, в ней вставка версии, `enqueueMemoryJobs(COMMIT_JOB_KINDS)`, `markMemoryStaleOnCommit` и удаление черновика. До принятия ни `current_version_id`, ни память, ни `chapter_drafts` не трогаются — `DELETE FROM chapter_drafts` из маршрутов генерации и правки убран. Принятие сверяется с ожиданиями **клиента** (`expectedVersionId`, `expectedDraftRevision`), а не с базой предложения: автор мог осознанно перечитать изменившуюся главу. Несовпадение — 409 `proposal_conflict` с `details.reason` (`version`/`draft`/`status`/`stale`), кандидат при этом цел, правки автора целы. Повтор с тем же `requestId` возвращает ту же версию (уникальный индекс по `accept_request_id`). Частичное принятие: сравнение по абзацам ([prose-diff.ts](packages/shared/src/prose-diff.ts), LCS, куски не пересекаются по построению), выбранное подмножество применяет сервер, память ставится на итоговую версию, а не на полного кандидата. Отмена — `POST /prose-proposals/:id/cancel`: сперва статус `cancelled` в базе, затем сигнал; прервать вызов подписки нечем, поэтому есть второй рубеж — перед записью результата раннер смотрит реестр и молча выбрасывает поздний ответ. Ревизия `chapter_drafts.revision` растёт на каждый автосейв; `NULL` в `base_draft_revision` значит «черновика не было вовсе» и отличается от ревизии 0. Статус критики считается от числа **запрошенных** критиков: `error` — не выжил никто, `partial` — часть, `done` — все; прежняя формула сравнивала число ошибок с длиной списка успешных и на четырёх падениях из четырёх рисовала зелёный отчёт.

**Один план книги (2026-09-06, фаза 5 конвейера):** этап `plot` сохранил идентификатор и потерял markdown-природу. Убрать его из `STAGE_IDS` было нельзя: `studioStateSchema` проверяет ключи сохранённых этапов по этому списку, и книга, куда интейк уже положил аспект сюжета, перестала бы читаться в тот же миг. Экран этапа — [PlanStagePage](apps/web/src/pages/PlanStagePage.tsx): варианты `books.outline_json` рядом, поглавные строки выбранного, «Утвердить план» и отдельный блок «Заметки из ваших материалов» с прежними аспектами, которые никуда не делись. Вариант плана получил необязательные `chapters` (строка на главу: `title`, `pov?`, `goal?`, `conflict?`, `stakes?`, `hook?`) и `source: "llm" | "author_material"`; повествовательные поля варианта (логлайн, синопсис, арки) стали необязательными **в хранилище** и остались обязательными в тулсхеме агента — тот же приём, что у `architecture`, потому что авторское оглавление синопсиса не имеет, а генератор обязан его дать. `OutlinePanel` теперь бережёт каждое ослабленное поле: вариант без логлайна рисуется короткой карточкой, а не пустой подписью. Утверждение — `POST /books/:id/plan/approve` ([utils/plan-approve.ts](apps/server/src/utils/plan-approve.ts)): строки сопоставляются с существующими главами **по порядку**, не по названию (автор переименовывает главы, план — нет, и одно переименование рассыпало бы сопоставление); совпавшая глава получает намерение и сохраняет своё имя и текст, лишняя строка создаёт главу обычной разрежённой нумерацией (`MAX(order_index) + 10`), лишние главы не удаляются. Повторное утверждение обновляет намерения и не плодит глав. `PlanPanel` читает намерение из главы, поля ручного ввода больше нет; `OutlinePanel` со страницы «Главы» ушёл, на его месте ссылка на экран плана. Готовность этапа `plot` считается не по аспектам, а по `isPlanApproved(book.outlineJson)` — признак приходит в `computeStudioProgress`/`effectiveStageStatus`/`computeRecommendedNextStage` снаружи, потому что общий пакет книгу не читает; вызовы без признака сохраняют прежнее поведение. Стык с фазой 2 закрыт: фрагмент интейка получил необязательные `chapters`, разобранное оглавление становится вариантом плана с пометкой авторского (`landFragments` возвращает `planVariants`, а `runIntake` дописывает их в `outline_json`, не сдвигая выбор автора и не вытесняя авторские варианты при переполнении), а проза о сюжете без списка глав по-прежнему ложится заметкой — и заметка видна на экране плана. Быстрый сбор — `POST /books/:id/quick-start` ([utils/quick-start-run.ts](apps/server/src/utils/quick-start-run.ts)): раннер по образцу приёма материала (SSE, `ping` раз в 20 с, реестр отмены в памяти, снимок для `inflight`, останов между этапами — прервать идущий вызов агента нечем). Он зовёт те же функции агентов, что обработчики Мастерской (`runAspectPlaybook` → `runAspectVariants`/`runAspectEntityVariants`, для плана — `runBookPlanning`; ради этого `loadBookContext` экспортирован из маршрута сюжета), пишет список разделов до генерации вариантов (иначе пятиминутное ожидание с упавшим бэкендом кончалось пустотой) и готовит черновики мира, лора, персонажей, предметов и плана в статусе `reviewing`, **ничего не утверждая и глав не создавая**: правило «без автора ничего не утверждается» держит интейк и предложения прозы, и кнопка быстрого сбора его не отменяет. Этап, где уже есть черновики, пропускается; отказ одного этапа не уносит остальные. Разделы одного этапа пишутся по три разом и друг друга не видят — та же плата, что у пакетной генерации в `AspectRunner`.

**Документные этапы (2026-09-22, фаза 3 конвейера):** «Мир» и «Лор» перестали быть списком аспектов с вариантами на каждый. Внутри модель прежняя — раздел документа и есть аспект `studio_state`, — снаружи этап проходится двумя нажатиями и одним ожиданием. У кнопки сборки три подписи, и каждая обещает ровно то, что сделает: «Собрать мир/лор» на пустом этапе, «Дописать недостающее (N)» — когда N разделов пусты, «Дополнить документ» — когда заполнены все; промпту агента `aspect_document` ([document.ts](packages/agents/src/aspects/document.ts), один вызов на весь документ, свой `timeoutMs` 600 с и `maxTokens` 16000) отвечают те же три ветки (собрать 5–9 / дописать пустые / добавить 1–4 недостающих и ничего не переписывать) — до этой правки полный этап получал разом «ничего не переписывай» и «собери 5–9 разделов». Прежняя связка «плейбук → варианты на каждый раздел» стоила семи вызовов и стольких же ожиданий. **«Есть текст» не считается по вариантам в статусе `superseded`/`rejected` и не доверяет `selectedVariantId`, указывающему на такой:** прежний `AspectRunner` при уточнении помечал вариант `superseded`, не снимая выбор, и у разделов мира/лора, заведённых до фазы 3, выбор так и указывает на мёртвый вариант — довериться ему значило бы показать устаревший текст, счесть раздел заполненным (сборка не дописала бы его) и утвердить кнопкой «Утвердить» отвергнутый вариант. Раздел, чьё имя модель повторила в одном ответе дважды, засчитывается один раз. Перегенерация принятого раздела снимает его `finalPayload` (иначе старый принятый текст оставался бы на экране поверх нового, оплаченного варианта); ручную правку наследует вариант, который автор ВИДЕЛ (`currentVariant`), а не тот, что стоит в записанном выборе. Запись всего этапа (сборка, утверждение) на 409 перечитывает этап и строит изменение заново от свежего состояния — обе операции чистые функции этапа, а слияние по построению не трогает разделы с текстом; раньше конфликт выбрасывал оплаченный документ, а экран слал на запись протухшую ревизию и дальше. Запись одного раздела держится прежнего правила: повтор только если именно этот раздел за это время не тронули. Правила слияния существуют дважды — [documentSections.ts](apps/web/src/components/studio/aspect-engine/documentSections.ts) на вебе и `quick-start-run.ts` на сервере — нарочно: общего кода между apps для документных этапов нет, но правило обязано совпадать пункт в пункт; проверка «этап занят» быстрого сбора для документных этапов теперь считает по тому же правилу «есть текст» (раньше занятость решал факт существования любого варианта, и этап с одними отвергнутыми вариантами быстрый сбор пропускал как «уже есть черновики»). «Ничего нового не добавилось» после сборки — нейтральный статус на экране, не красная ошибка. Всё приходит в статусе `reviewing`: правило «без автора ничего не утверждается» кнопка сборки не отменяет. Текстовая заметка-затравка у отдельного раздела («свой черновик») ушла вместе с `AspectRunner`; вместо неё — заметки автора уровня этапа (`StageState.authorNotes`, предел 4000 символов, миграции не нужно — это JSON-колонка), которые уходят в каждую сборку — кнопку и быстрый сбор: вызов идёт минутами, и терять набранное при обновлении страницы нельзя. Сохраняются они и сами по себе, по уходу с поля (`onBlur`), а не только вместе со сборкой или утверждением. «Переписать» и «Другие варианты» отдельного раздела заметки НЕ видят: маршруты `aspect_refine`/`aspect_variants` их не читают — учитывает заметки только сборка документа. Заодно снесён `mockGenerator.ts` — у него не осталось вызывающих. У раздела три действия, и все три бьют в уже существовавшие маршруты: «Переписать» — `aspect_refine` по указанию автора, «Другие варианты» — `aspect_variants`, «Править» — ручная правка, сохраняемая принятым вариантом `manual`. `AspectRunner` удалён целиком: после переезда экрана у него не осталось вызывающих, а пакетная генерация «Сгенерировать все оставшиеся» ушла вместе с ним — она существовала ровно потому, что раздел стоил отдельного вызова. `PlaybookRunner` остался, им пользуется этап персонажей. И `deriveStageStatus` больше не выводит `skipped` из «все разделы улажены, ни один не принят»: это и был дефект «ничего не принял = готово», из-за которого рекомендатор вёл дальше с пустого этапа. `skipped` ставит только явная кнопка автора — «Этап не нужен» у необязательных этапов, «Пропустить этап» у остальных (обе кнопки одного `StageSkipControl`, обе пишут один и тот же статус) — и никогда не выводится из состояния разделов. Этап, которого коснулось прежнее правило (оно выводило `skipped` из «всё улажено, ничего не принято»), хранит тот же статус и после починки: он неотличим от явного пропуска, а вернуть такой этап автор может кнопкой «Вернуть этап». Предметы в фазу 3 не вошли намеренно: они материализуются в таблицу `items`, которую читает агент лора, и перевод их в прозу разорвал бы эту связь — их закрывает фаза 4 вместе с персонажами.

**Замысел сцены не считается дважды (2026-09-22, живой прогон):** «Дописать с беата» продолжает ТУ ЖЕ сцену того же плана, а подготовка сцены — отдельный вызов модели на минуту: живой прогон намерил 46–50 с на неё при 31–37 с на сам беат, то есть больше половины ожидания уходило на пересчёт уже известного. При `fromBeat > 0` маршрут берёт `chapters.scene_intent_json` через [`loadStoredSceneIntent`](apps/server/src/utils/scene-intent.ts) вместо нового вызова. Сохранённое не принимается как есть: снимок контекста пересобран, поэтому ссылки на события сверяются с НОВЫМ снимком (AC-25 держится и на переиспользовании), а участник, которого в сцене больше нет, уходит вместе со своими напряжениями — карточки у него в промпте всё равно нет. `null` (строки нет, не разбирается, печатать нечего) означает обычный путь: тихо остаться без замысла хуже, чем заплатить за вызов. Прогон с первого беата считает заново — там сцена начинается, а не продолжается.

**Персонажи V2 (2026-09-17, этап 2 индивидуальности персонажей):** профиль персонажа получил `schemaVersion: 2` и разъехался на две схемы. `characterProfileV2Schema` — схема чтения: без пределов длины, без обязательных полей, с `extra`, куда уезжает всё, чего она не знает. `characterProfileWriteSchema` — схема записи, с пределами, применяется только в маршрутах создания и изменения. Разделение не косметическое: `toCharacter` звал `schema.parse`, и одна кривая строка роняла `GET /books/:id/characters` на всю книгу, а срезанные неизвестные ключи и были той потерей `role/age/background`, которую искали (поля всё это время лежали в `profile_json` — терялись они на чтении, не на записи). Миграция 0022 поэтому чисто структурная: `revision` у персонажей и отношений, `profile_json` у отношений, общая полиморфная история `entity_profile_versions` и банк `character_voice_samples`; ни одна строка `profile_json` не переписана. `PATCH /characters/:id` и `PATCH /relationships/:id` требуют `expectedRevision` **обязательно** — переходного режима не заводили, потому что с необязательным полем два изменения с одной базой молча перезаписывают друг друга; несовпадение — 409 `revision_conflict` с текущей ревизией в `details`. Ревизия никогда не растёт без строки истории: обе записи — и при создании, и при обновлении — идут одной транзакцией [entity-revisions.ts](apps/server/src/utils/entity-revisions.ts), потому что без историй для ревизии 0 авторская исходная версия не восстанавливается. Отношения остались направленными: A → B и B → A — две независимые строки со своими качествами (доверие, уважение, привязанность, зависимость, страх, долг, обида, ожидания, разногласия, умолчания, регистр), и ни одно из них не вычисляется из `tension` — «-0.9» и «боится» разные сведения. Образцы речи отбираются [`selectVoiceSamples`](packages/shared/src/character-voice.ts) детерминированно: только принятые, только не из будущих глав относительно границы сцены, дальше вес по ситуации и адресату и стабильный порядок по id. `ORDER BY random()` здесь запрещён по той же причине, что и в подборе стилевых примеров: образцы попадают в кэшируемый префикс промпта. Граница сцены передаётся в `characterContextToPrompt` параметром `chapterOrder` полем `excludeFromChapterOrder` — **исключающая**, отличается от **включающей** `beforeChapterOrder` в `chapter-retrieval.ts`, где идёт `order - 1`; именно это предотвращает утечку реплики персонажа из главы в подготовку самой этой сцены. Выбор регистра диалога приходит на этапе 5 конвейера (SceneIntent) и пока при сборке контекста не используется. Материализация состава перестала быть `INSERT`-ом: кандидат с `materializedEntityId` обновляет свою строку и наращивает ревизию, поэтому второе «Добавить в канон» правит героев, а не удваивает их; ключ повторного запроса включает отпечаток профилей с рекурсивно отсортированными ключами, чтобы авторская правка попала на ветку обновления вместо переиспользования старого ответа классификатора. `resolveEntity` на двух героях с одинаковым нормализованным именем возвращает `null` вместо первого попавшегося — тихий выбор пришивал факт чужому герою и всплывал только в готовой главе. `createVoiceSampleInputSchema` не принимает `status`: статус выводится из `origin` на сервере, так что черновик модели не приходит в уже принятом виде — это воплощение главного правила этапа, «ничего не утверждается без автора». Отдельного экрана карточки в этом этапе нет намеренно: он проектируется один раз под «составы» фазы 4 конвейера, а авторское редактирование V2 пока живёт во вкладках `KnowledgePanel`.

**Сцены и память (2026-09-19, этап 3 индивидуальности персонажей):** знание героя — это вид события, а не своя таблица: два источника истины расходятся на первой же правке. `character_events` хранит четыре вида — `knowledge`, `state`, `relation_shift`, `commitment` — и читается **на границе сцены**, исключающей: секрет из главы 8 не попадает в подготовку главы 4, а то, что герой узнаёт в самой сцене, в её начальный контекст не входит. Граница ИСКЛЮЧАЮЩАЯ, в отличие от включающей `beforeChapterOrder` в `chapter-retrieval.ts`, которая передаёт `order - 1`; путать их нельзя, это и есть утечка, ради которой этап затеян. Порядок главы берётся **join'ом к `chapters`**, а не денормализованной колонкой: перестановка глав иначе оставила бы тихо неверную границу, и заметить это было бы нечем. `chapter_id` у события — `ON DELETE CASCADE`, а не `SET NULL`: пустая глава значит «известно с начала» и видно на любой границе, поэтому при `SET NULL` удаление восьмой главы превращало записанный в ней секрет ровно в такую запись. **Вся SQL границы живёт в одном месте** — [character-events.ts](apps/server/src/utils/character-events.ts); `packages/agents` до сервера не дотягивается, поэтому `gatherCharacterContext` принимает читателей (`CharacterBoundaryReaders`), а сервер даёт их через `makeCharacterBoundaryReaders`. Второй экземпляр этой SQL заводить нельзя: он уже появлялся и разошёлся бы молча именно на пути к Писателю. `order_index` разрежённый (шаг 10) — расстояние в главах считать только через [`chapterPositionLookup`](apps/server/src/utils/chapter-position.ts); порог свежести состояний, сравнивавший сам `order_index`, не срабатывал никогда после четвёртой главы книги.

Доказательство обязательно: у события есть дословная цитата, и без неё оно не активируется (AC-25). **Диапазона модель не присылает** — просить у неё позиции символов в главе на двадцать тысяч знаков значит просить то, чего она не умеет, и промах на единицу отвергал бы каждое событие, а разбор возвращался бы пустым, неотличимо от «в главе ничего нет». Цитату ищет сервер, [`locateEvidence`](apps/server/src/utils/character-events.ts); встречающаяся дважды отвергается — неоднозначная привязка хуже отсутствующей, то же правило, что у `resolveEntity` на тёзках. Модельный ответ не считается доверенным потому, что он правильной формы. Сдвиг отношения активируется как **гипотеза** (`defaultVerificationFor`), а не как факт: одна резкая реплика не делает «презирает всех» правдой. Услышанная ложь — знание героя с `acquisition: "told"`; объективный канон книги от его убеждений не меняется. У `acquisition` пять значений, пятое — `unknown` с пустой подписью: у перенесённых и введённых вручную знаний происхождения нет, и `observed` вместо него — выдуманное сведение (INV-07); извлекателю это значение недоступно, схема его отвергает. Эпизодическое состояние не тянется бессрочно: `scope` «сцена»/«глава» кончается вместе со своей главой, `endsAtChapterOrder` закрывает состояние явно, а наблюдение старше трёх глав отдаётся как «наблюдалось в главе N», а не как нынешнее.

Нового вида задания в `memory_jobs` **не** заводили: список зашит в SQL `CHECK`, а SQLite не меняет `CHECK` через `ALTER TABLE`. Расширен контракт задания `facts`, `MEMORY_PIPELINE_VERSION` поднят до 2. **Само это повышение ничего не переразбирает** — задания ставятся только на свежесозданную версию главы, у которой строк нет ни под какой версией; события появятся лишь у глав, зафиксированных после выпуска, а у написанной раньше книги — только после «Перестроить память с главы N». События активируются внутри той же транзакции, что факты и заметки ([memory-activation.ts](apps/server/src/utils/memory-activation.ts)): версия ложится целиком или никак (AC-22). Бросок в этой транзакции опаснее, чем кажется — задание `facts` к тому моменту уже `done`, и память версии теряется молча и навсегда, поэтому испорченный стадированный результат (`JSON.parse(...) as T`, без схемы) не бросает, а просто не даёт события. `INSERT OR IGNORE` при записи событий — намеренное отличие от `recordProfileVersion` этапа 2, где `OR IGNORE` был убран: там дубликат означал потерянное обновление, здесь он означает повторную обработку той же версии, чего AC-21 и требует; ключ дедупликации считается по смыслу (`normalizeEventData` + NFC), а не по сырому JSON, иначе дописанное моделью `source: null` разводило одно событие на два.

Заодно починены два дефекта сводки ранних глав, портившие текст каждый день. Она бралась **без границы**: при генерации главы 10 в промпт уходил пересказ вплоть до двадцатой. И пропускалась по совпадению **диапазона**, а не содержимого, поэтому правка главы 3 внутри диапазона 1–20 сводку не обновляла никогда — теперь у `book_meta_summaries` есть `source_fingerprint` (миграция 0024) из троек «глава: версия: название» — название входит потому, что уходит в промпт сводки, и переименованная глава упоминается в ней прежним именем. Отпечаток сверяется и при чтении, а не только при пересчёте. Сводка больше не одна на книгу: уникальность по `(book_id, covers_to_order)` (миграция 0025), у книги живёт по сводке на каждый пройденный рубеж, и сцена берёт самую полную из кончающихся ДО своей границы. Прежде строка была одна и всегда покрывала всё, кроме последних трёх глав, поэтому на границе десятой главы не годилась никогда и три десятка ранних глав уходили в промпт поглавно. Миграция 0023 переносит `character_knowledge` в события со статусом `confirmed` и происхождением `migration`; **старая таблица не удаляется** — страховка на случай, если перенос окажется неверным.

**Молчаливые потери памяти (2026-09-19, закрытие долгов этапа 3):** разбор главы умел молчать четырьмя способами, и все четыре выглядели на экране как «память актуальна». (1) Негодная строка ответа валила весь `safeParse`, унося вместе с собой факты и заметки главы; теперь `canonFactExtractionSchema` отдаёт непринятый элемент как `null`, а отсеивает и считает его сервер. `.transform` внутрь схемы класть нельзя — по ней строится инструмент модели, а `z.toJSONSchema` на трансформации бросает. Жёстким остался только предел длины массива: превышение значит, что модель не поняла контракт. **Общий контекст (2026-09-19, этап 4 индивидуальности персонажей):** контекст для Writer, критиков и Reviser собирает **одна функция** — [`assembleGenerationContext`](apps/server/src/utils/generation-context.ts). До неё было две сборки, и они расходились в трёх местах, которых никто не видел: критика получала историю срезом первых 1200 символов каждой предыдущей главы (без сводок, хвоста и поиска), читала премису сырой колонкой и получала «(не задана)» там, где Writer выводил её из замысла, и не бюджетировала студийный контекст. Роли различаются только **представлением** — что сканировать (план у Writer, текст главы у критики), чем искать, сколько стилевых образцов (критикам ноль, иначе они ищут совпадения с образцом вместо стиля); история, участники на границе, факты, лор, бюджет — одни. `routes/plot.ts` и [`chapter-prose-context.ts`](apps/server/src/utils/chapter-prose-context.ts) — тонкие адаптеры над ней. Блок истории у критиков и Reviser рендерит одно место — `renderHistoryBlocks` в [critics/base.ts](packages/agents/src/critics/base.ts): он был переписан шесть раз, и каждая копия знала только о пересказе. **Бюджет один на всех** — `MAX_PROSE_CONTEXT_TOKENS`; карточки участников с их знаниями и фактами — обязательный слой (`required`), и если он не помещается, `compileContext` отдаёт `requiredOverflow`, а Writer, критика и правка отвечают 400 одним текстом (`requiredOverflowMessage`) до первого токена — генерировать с урезанными ограничениями, о которых модели не сказали, хуже отказа (раздел 8.4 ТЗ). Поиск по тексту исключает **только главу, поданную дословно** (`verbatimChapterOrders` — хвост предыдущей главы), а не всё окно: окно даёт пересказы, и деталь, не попавшая в пересказ, иначе недостижима (AC-12). **Манифест источников** ([context-manifests.ts](apps/server/src/utils/context-manifests.ts), миграция 0026): на каждую сборку — версии предыдущих глав, ревизии **всех** героев и отношений книги, события всех героев на границе сцены (`loadEventsAtBoundary`), стиль, отпечаток outline, что вошло в бюджет, и отпечаток НАБОРА источников (`snapshotFingerprint` в shared, без `node:crypto` — пакет общий с браузером). Источники считаются по **базе книги на границе**, а не по тому, что попало в карточки: Writer сканирует план, критика — текст главы, и глава, введя героя, которого в плане не было, давала бы разные карточки при той же базе — отпечаток по карточкам кричал бы «база уехала» на каждой второй главе, и автор перестал бы ему верить. Отпечаток по набору, а не по тексту промпта: представления ролей различаются намеренно. Манифест Writer'а привязывается к версии при принятии кандидата (`prose_proposals.context_manifest_id`); критика сверяет свой с ним и пишет в отчёт `baseChanged` — true/false/**null** («сравнивать нечем» не сводится к «не изменилась»). Не блокирует: автор мог поправить героев осознанно. **Текст промпта не хранится** — решение автора 2026-09-19, отклонение от раздела 8.1 ТЗ: всё, на что указывает манифест, версионировано, и хранить второй экземпляр правды размером с промпт на каждую генерацию — рост базы без единого читателя; добавляется, когда появится читатель (экран «что видела модель»). Это другой отпечаток, чем `prose_proposals.context_fingerprint` этапа 1: тот грубый (план, версия, `books.updated_at`) и отвечает на «уехала ли база, пока модель писала кандидата»; этот — по источникам и отвечает на «уехала ли база между написанием и критикой». Резолвер различает «неизвестно» и «неоднозначно» (`resolveEntityDetailed`): два героя с одним именем — решение автора, имя отдаётся наверх в `ambiguousNames`, а не подменяется первым попавшимся.

**Контракт главы (2026-09-19, слайс 4.5):** беат-лист говорит, КАКИЕ сцены идут в главе; контракт — что глава обязана сделать и чего делать не вправе. Четыре списка в варианте поглавного плана ([plot.ts](packages/shared/src/plot.ts), `chapterContractSchema`): `mustHappen`, `mustNotHappen`, `expectedRevelations`, `allowedCanonSupersessions`. **Необязателен в хранилище, обязателен в тулсхеме планировщика** — тот же приём, что у `architecture` и `closing`: старые `plan_json` читаются, а свежий план обязан определиться, потому что «не задано» и «ничего не запрещено» для критиков неразличимы. Без контракта критик канона блокировал ровно тот поворот, ради которого глава пишется: «выясняется, что брат жив» — противоречие действующему факту «брат погиб». Поэтому `allowedCanonSupersessions` — единственный способ разрешить главе противоречить канону; разрешение на один факт не снимает проверку с остальных. Отмена несёт обязательную формулировку (`statement` → `becomes`) и необязательный `fact_<id>`: планировщик впервые видит действующие факты (`renderActiveFactsPrompt(..., { withIds: true })`, граница та же, что у Writer), но список не всегда непуст. Рендер один на всех — `renderChapterContract`; два разошлись бы, и критик судил бы по одной формулировке, а Писатель работал по другой. Пустые подсписки не печатаются нигде, включая интерфейс: заголовок без строк читается как «ничего не запрещено». У Писателя контракт идёт после beats и перед финалом, и правило называет приоритет прямо — **запрет сильнее беата** (план порождает одна модель, и она способна положить в beats то, что сама же запретила). Редактор проверяет выполнение: пропущенное `mustHappen` и нарушенный запрет — `blocking`, нераскрытая тайна — `suggestion`; замечание о невыполненном обязательстве — **единственное, где цитата не требуется** (цитировать отсутствие нечем, и без явного исключения критик либо молчит, либо выдумывает цитату). Reviser тоже получает контракт, и он сильнее замечаний: критик смотрит текст, а не план, и вправе предложить убрать сцену, которую план объявил обязательной, — а правка последний проход. Ручной правки контракта пока нет: план меняется выбором варианта или перегенерацией.

**Порядок главы переезжает вместе с её памятью (2026-09-19, К1 независимого ревью):** `chapters.order_index` меняется ровно в одном месте — `POST /books/:id/chapters/reorder` ([chapter-reorder.ts](apps/server/src/utils/chapter-reorder.ts)), и `updateChapterInputSchema` стал `strictObject` без `orderIndex`, чтобы второй путь нельзя было завести случайно. Причина: порядок хранится копиями в пяти таблицах (`chunks.chapter_order`, `book_facts.valid_from_chapter`/`valid_to_chapter`, `book_notes.chapter_order_introduced`/`chapter_order_resolved`, `character_voice_samples.source_chapter_order`, `book_meta_summaries.covers_*`), и каждый читатель границы сцены сравнивает именно копию. Перестановка, менявшая один `chapters.order_index`, оставляла их числами прошлой раскладки — глава, уехавшая в конец, проходила фильтр «до главы N» и попадала в подготовку ранней сцены (доказано живым прогоном: чанк главы А с `chapter_order` 10 при фактическом 30 возвращался на границе 19). Единственный слой, который переживал перестановку сам, — `character_events`: там порядок берётся join'ом к `chapters`. Список приходит **целиком**: N запросов по главе оставляли бы книгу в промежуточных раскладках, а перенос считается от карты «весь старый порядок → весь новый». Копия, у которой есть путь к своей главе (`source_version_id`, `chapter_id`), переносится **по главе** — это точно; остальные по значению. Переносится и `hooks.expected_resolution_chapter_order` — шестая копия, на промпты не влияющая, но показывавшая автору чужую главу. Чего перенос не обещает: `valid_to_chapter` — это «порядок отменившей главы минус один», и перестановка, меняющая относительный порядок двух глав, ломает сам смысл интервала. Он пересчитывается от новой позиции отменившего факта, а вывернутый схлопывается в «факт жив только в своей главе». У факта без `superseded_by` (перенесённые данные) конец берётся **не по самой поздней главе интервала, а по первой главе ЗА ним минус один**: глава, лежавшая после интервала, могла встать между его главами, и «до самой поздней» вернуло бы отменённый факт туда, где его не было, — та же утечка, ради которой всё это. Заметка, чья закрывающая глава уехала раньше вводящей, схлопывается в «открыта и закрыта в одной главе»: пара «закрыто раньше введено» не нашлась бы ни на одной границе и пропала бы молча. Сводки по рубежам удаляются (их отпечаток всё равно не сошёлся бы), книга помечается `memory_stale_from_chapter_order` с самой ранней сдвинувшейся позиции. Отметка **советующая**: `maybeClearMemoryStale` снимет её на следующей активации, потому что версии глав не менялись; настоящая пересборка — «Перестроить память с главы N».

**Текст автора становится версией прежде, чем что-либо его заменит (2026-09-19, К2):** `chapter_drafts` — одна строка без истории, единственная копия того, что автор напечатал после последней версии, и её удаляли три пути, не сохранив: принятие кандидата (текстом версии становится кандидат, а не черновик), `restore` и коммит содержимого редактора из предпросмотра (клиент шлёт текст версии, а черновик новее). Теперь все три зовут `preserveDraftAsVersion` ([chapter-drafts.ts](apps/server/src/utils/chapter-drafts.ts)) внутри своей транзакции. Снимок — `source: 'manual'`, становится родителем следующей версии и **не ставит заданий памяти**: его тут же вытесняет версия вызывающего, и задания ушли бы в `obsolete` первой проверкой `isCurrent`. Снимка не будет, если черновик пуст (редактор не автосохраняет пустой документ), совпадает с текущей версией (автосейв без единой правки) или совпадает с тем, что вызывающий сам сейчас коммитит — по строке JSON **или по тексту**: редактор нормализует документ при загрузке, и черновик, записанный сервером раньше, перестаёт совпадать байт в байт, хотя автор ничего не менял. Вторая половина того же — на клиенте: `onSave` досылает отложенный автосейв перед коммитом (`mark` + `flushNow`), иначе черновик десятисекундной давности честно становился отдельной версией и на один осознанный Ctrl+S приходилось две. В предпросмотре не досылает: там в редакторе текст старой версии, и автосейв затёр бы настоящий черновик. В `acceptProposal` снимок делается ПОСЛЕ всех проверок, читающих текущую версию (CAS версии и ревизии черновика, `contextFingerprint`, слияние `selectedChangeIds`, `countRepairAncestors`), иначе они судили бы о базе, которой автор не видел.

**Концепт пишется поверх свежего, а не поверх снимка (2026-09-19, К3):** `books.concept` — JSON без ревизии, и три вызывающих читали его ДО многоминутного вызова модели, а записывали объект, собранный из прочитанного: интейк (`{...concept, idea}`), генератор питчей и смешивание (`{...concept, pitches: [...]}`). Всё, что автор делал в Мастерской, пока шёл разбор — новые питчи, утверждённый замысел, правки строк, — возвращалось к состоянию начала прогона. Теперь каждый из трёх перечитывает концепт непосредственно перед записью и вносит только своё поле; интейк заодно проверяет **свежий** `idea`, а не прочитанный в начале, поэтому замысел, напечатанный автором во время разбора, не перезаписывается машинным. Остаточный риск: `PATCH /books/:id/concept` по-прежнему полная замена — две вкладки на форме замысла перетирают друг друга.

**Материализация состава сливает профиль, а не заменяет (2026-09-19, К4):** кандидат Мастерской несёт пять полей (`name/role/age/background/description`), карточка V2 — ещё цели, ценности, принципы, противоречия, профиль голоса и план автора. Повторное «Добавить в канон» писало `profile_json` целиком из кандидата и сбрасывало всё остальное в умолчания. Теперь накладываются только ключи, которые кандидат действительно прислал (`mergeCharacterProfile` в [character-profile.ts](packages/shared/src/character-profile.ts)); `null` считается «не знаю» генератора, а не командой стереть — очистить поле автор может правкой карточки. Не накладывается и ключ, чьё значение нормализация увезла в `extra` (пришло не той формы): на его месте она оставляет умолчание схемы, и положить пустой список вместо авторских целей — та же потеря, только тише. Пустой список кандидата тоже пропускается: полей-списков он не несёт вовсе, и пустота у него значит «не знаю». Имя, которого у кандидата нет, тоже не затирается. У предметов схемы V2 нет, но правка через `PATCH /items/:id` терялась так же — там слияние поверхностное. Плюс необязательный `expectedRevision` у кандидата: вкладка возит `materializedRevision` туда-обратно через `entityCandidateSchema`, и несовпадение даёт 409 `revision_conflict` вместо тихой перезаписи. Ревизия входит в ключ идемпотентности — иначе повтор того же тела ПОСЛЕ правки карточки доставал бы из журнала кэшированный успех и прятал конфликт, о котором тело как раз и спрашивает. Необязательный намеренно — вкладка, ничего не знающая о ревизии, по-прежнему обновляет героя, но уже слиянием; сбой записи `studio_state` после материализации теряет ревизию, и следующее «Добавить в канон» пойдёт без проверки, опираясь только на слияние.

**Поиск отвязан от извлекателей, очередь — от упавшей главы (2026-09-19, В1/В3/В4/В5/В6/В7 ревью):** «чанки в индексе» и «производная память активирована» — два разных факта, и теперь у них две колонки. `chapters.indexed_version_id` (миграция 0027) ставит задание `index`, и по нему же фильтрует поиск; `memory_version_id` остался за фактами, заметками и событиями. Прежде поиск читал `memory_version_id`, то есть требовал завершения всех четырёх заданий коммита — трёх через модель: недоступный бэкенд делал главу невидимой полнотекстовому поиску, который от модели не зависит вовсе. По той же причине `insertChapters` больше не ставит `memory_version_id` руками: это была ложь про разобранность — импортированные главы числились «память актуальна», не имея ни сводки, ни фактов, ни заметок, ни событий, и автор с десятью готовыми главами не узнавал, что Писателю одиннадцатой подают первые 1200 символов каждой предыдущей. Импорт ставит `indexed_version_id` (правду) и обычные задания очереди. В самой очереди `error` перестал быть блокирующим статусом: задание, исчерпавшее пять попыток, не «вот-вот доделается», и, считая его таким, очередь останавливала факты и заметки ВСЕЙ книги из-за одной главы. Отказ авторизации прямого API (`status` 401/403) теперь терминален — пять повторов на неверном ключе были часом ожидания вместо ответа. Удаление главы уносит её машинные факты и заметки (связь — через `source_version_id`; авторские `manual`/`studio` остаются) и называет их числом, как уже называло события. «Перестроить память с главы N» наконец перестраивает: удаляет извлечённое (`origin = 'extracted'`, у событий `llm`) от N и дальше, снимает пересказы версий и `memory_version_id`, открывает обратно факты и нити, закрытые удалённым, и только потом ставит задания — прежде производные строки оставались, и получалось объединение старой памяти с новой. Сводки по рубежам: читатель берёт самую позднюю ПРИГОДНУЮ (проверяя отпечаток), а не просто самую позднюю — одна негодная строка отправляла всю книгу на поглавные пересказы, хотя рядом лежал живой рубеж пораньше; `runMetaSummary` вдобавок пересобирает устаревшие рубежи, не больше четырёх за прогон, чтобы правка первой главы не превратилась в десятки вызовов разом. И граница канона: у Писателя и планировщика она теперь `order_index - 1` (`factsBoundary: "before_chapter"`), а не сам номер главы — у главы может быть принятая версия, и её факты с заметками описывают текст, который автор как раз переписывает. У критики граница прежняя, включающая: она проверяет главу против того, что глава же и утверждает.

**Обрыв потока и неудавшееся сохранение больше не молчат (2026-09-19, В9/В10/В11 ревью):** чтение SSE вынесено в одно место — [`consumeSse`](apps/web/src/api/sse.ts); шесть читателей в `client.ts` повторяли разбор кадров, и все шесть на оборванном соединении просто заканчивали цикл: экран оставался в «идёт генерация» навсегда. **Порядок разбора глав больше не обязателен (2026-09-19, ревью ветки высоких правок):** убрав `error` из блокирующих статусов очереди, мы сняли гарантию, на которой молча держался `persistExtractedFacts`: он чистил «эту главу и все последующие» и искал предшественника только среди ОТКРЫТЫХ фактов, потому что поздних строк в базе быть не могло. Теперь могут: задание, упавшее навсегда, очередь не держит, и «Повторить» по четвёртой главе приходит после того, как пятая разобрана. Три следствия закрыты разом. Предварительная чистка сузилась до `valid_from_chapter = chapterOrder` — прежнее `>=` стирало факты всех глав, разобранных позже. Предшественник ищется ближайший по `valid_from`, независимо от того, закрыт ли он, и закрывается только если действует на этой главе (`priorCovers`) — иначе интервалы перекрывались. И новый факт закрывается ближайшим ПОЗДНЕЙШИМ (`closeAgainstNextFact`), иначе он оставался действующим навсегда и Писатель шестой главы получал два противоречащих факта. `lower()` в SQLite работает только по ASCII: сравнивать кириллические имена через него нельзя, поиск идёт по `entity_name` как есть. Реоткрытие фактов при удалении главы и при «Перестроить память» теперь точное — открывается тот, кого закрывает удаляемый (`superseded_by IN (…)`, до удаления, пока связь цела), а не всякий закрытый без ссылки: без ссылки живут и интервалы от перестановки глав, и перенесённые, и закрытые автором, и перестроение с первой главы реанимировало почти весь закрытый канон. Нити открываются обратно только машинные (`origin = 'extracted'`): отличить «закрыл автор» от «закрыла модель» у заметки нечем, а стереть авторское решение хуже, чем оставить нить закрытой. Добор устаревших рубежей сводки идёт только при пустой очереди пересказов книги — «Перестроить память» ставит задание на главу, каждое цепляет свой `rollup`, и добор на каждом умножал платные вызовы на число глав. Импорт больше не ставит задание `index`: чанки маршрут кладёт сам, синхронно, чтобы поиск видел принесённые главы сразу, а второе задание означало бы повторную индексацию той же версии (`indexChapterVersion` чистит чанки перед вставкой, и совпадение по времени удваивало часть). Если синхронная индексация упала, задание ставится в очередь — иначе глава не нашлась бы никогда. Быстрый сбор считает этап занятым по отсутствию НЕзаполненных разделов: «хотя бы один с вариантами» пропускало этап, где собрались три из пяти. На фронтенде: `consumeSse` нормализует CRLF (разделитель кадров ищется как `

`, и на потоке с `
` не находился бы ни разу), склеивает кадр из нескольких строк `data` и отпускает читателя в `finally`; повторы `useDebouncedSave` кончаются вместе со списком пауз — отказ, который сам не пройдёт, иначе стучал бы раз в полминуты до закрытия вкладки; `AspectRunner` повторяет запись на 409, только если ЭТОТ раздел за это время не трогали, иначе показывает автору, что его текст на экране, а чужая правка иначе пропадёт.

**Вложенный массив приходит строкой (2026-09-20, живой прогон):** извлечение фактов не работало ни на одной главе. Схема `canon_fact_extractor` — самая сложная в проекте: два массива объектов, у событий вложенный `data` со своим видом у каждого. Модель на такой схеме сериализует второй массив в JSON-строку — так устроена передача аргументов инструменту MCP, и это её выбор, не ошибка. Дальше ломалось всё: SDK проверяет аргументы САМ, до обработчика, и отвечал модели `MCP error -32602` («expected array, received string» и одновременно «too_big: expected string to have <=30 characters» — предел длины массива применялся к строке). Модель читала ответ, пыталась переформатировать, упиралась в предел ходов. Три правки в [mcp-submit-tool.ts](packages/llm/src/clients/mcp-submit-tool.ts). `toolFacingSchema` отдаёт SDK ослабленную копию схемы, где каждое поле верхнего уровня дополнительно принимает строку: строгая проверка живёт в обработчике, куда вызов теперь доходит. `parseJsonStringFields` разворачивает строку обратно в массив или объект. А строка, которая начинается как массив и **не разбирается**, становится пустым массивом: модель ломает экранирование на русских кавычках и переносах, восстановить содержимое нельзя, но факты в том же ответе приходят настоящим массивом и целы — ронять их из-за соседнего поля значило терять память всей главы каждый раз. Объект так не подменяется: у него нет безопасного пустого значения. У `canon_fact_extractor` поднят `maxTurns` до 6 — трёх ходов не хватало даже на исправимых ответах. Проверено живьём: до правок 0 фактов на любой главе, после — 23 факта и 13 заметок на главе в 2372 слова. События персонажей из того же вызова по-прежнему теряются (их массив и есть та повреждённая строка); лечится разделением на два вызова, это отдельная работа.

Эвристика проверяемая — разбор всё равно идёт через `JSON.parse`, и неудача остаётся неудачей. Проверено живьём: строка в 7955 символов, где `JSON.parse` падал на 3955-м, после ремонта дала 15 событий. **Эти 15 событий в таблицу не легли, и это правильно:** активация отвергла их все с «имя героя не разрешилось». Книга разошлась в именах — питч назвал героиню Ниной, этап персонажей создал «Агату Солнцеву», план книги снова зовёт её Ниной. Механизм сработал как задумано (INV: не пришивать факт чужому герою), а расхождение имени между питчем и составом — отдельная задача конвейера.

**Имя героя держится одно на всю книгу (2026-09-20, расхождение имён):** героиню звали Ниной в замысле, Агатой Солнцевой в составе и снова Ниной в плане, и все пятнадцать извлечённых событий отвергались при активации с «имя героя не разрешилось». Разрыва было два, и оба в промптах. Генератор состава ([entity-variants.ts](packages/agents/src/aspects/entity-variants.ts)) получал из замысла только жанр, тон, аудиторию и логлайн: поле `premise.protagonist`, где и стоит выбранное автором имя, в промпт не попадало вовсе, и модель придумывала своё. Теперь печатаются протагонист, конфликт, ставки и крючок, а задание требует переносить названные в замысле имена дословно во ВСЕ варианты. Проверено живьём: три варианта состава, во всех трёх «Нина Соловьёва» и «Ворт Соловьёв». Второй разрыв — планировщик: `studioContextToPrompt` отдавал замысел, мир, лор и сюжет, но не утверждённый состав, поэтому план книги и план главы звали героев именами из питча. `loadStudioContext` читает `characters` (`loadCanonCast`, имя и роль, профиль разбирается врукопашную — одна негодная строка не должна лишать планировщик всего состава), а блок «## Персонажи книги (канон)» называет правило прямо: **канон сильнее замысла**, имя из списка и есть имя героя. Состав материализуется до этапа сюжета, так что к плану он готов. Заодно отказ перестал быть безымянным: `PersistEventsOutcome.unresolvedNames` несёт сами имена, они ложатся в `result_json` задания и доходят до экрана главы — «не прижилось записей: 2 — в составе книги нет: Нина, Ворт». Чего это не чинит: книгу, уже разошедшуюся в именах, — там лечит псевдоним (`POST /books/:id/entities/character/:id/aliases`) или переименование героя, а экрана для псевдонимов пока нет.

**Замысел сцены (2026-09-20, этап 5 ТЗ персонажей, слайс 1):** Писатель получал карточки героев — кто они, — но не получал, ЧЕГО каждый хочет в этой сцене, и герои действовали из описания, а не из намерения. Агент `scene_intent` ([scene-intent.ts](packages/agents/src/scene-intent.ts)) делает один вызов на сцену для всех участников и возвращает на каждого: цель здесь, на что смотрит, о чём молчит, как добивается своего, чем поступится, чего не сделает, плюс напряжения между участниками. Вызова на реплику нет и быть не должно — намерения осмысленны только рядом друг с другом. Бэкенд `subscription` (решение ТЗ): `maxTokens` и `temperature` до модели не доходят, поэтому размер держит `sceneIntentToolSchema`, а не параметр вызова, и у агента свой `timeoutMs` 600 с. Схем две, как у профиля V2 и плана главы: чтения (без пределов, строка из базы не должна ронять главу) и ответа модели (с пределами; `.strict()` — `sceneId` и `contextSnapshotId` от модели не принимаются, их ставит сервер, иначе она могла бы назвать чужой снимок).

**Ссылки на события сверяются со снимком (AC-25).** `relevantEventIds` пропускаются через `sourceRefs` той же сборки контекста: номер, которого в снимке нет, выбрасывается и считается, а не принимается потому, что ответ правильной формы. Второй SQL с собственной границей сцены здесь заводить нельзя — он разошёлся бы с карточками молча, и это ровно та утечка, ради которой границу держат в одном месте ([character-events.ts](apps/server/src/utils/character-events.ts)). Выдуманный участник (герой не из сцены) выбрасывается целиком: карточки у него в промпте всё равно нет.

Состав сцены теперь виден наружу — `AssembledContext.participants` ([generation-context.ts](apps/server/src/utils/generation-context.ts)): это тот же состав, из которого собраны карточки. По нему же критик персонажей слайса 2 решит, запускаться ли (на монологе вызов впустую). Подготовка не зовётся, если участников меньше двух. **Падение подготовки не срывает главу:** `prepareSceneIntent` возвращает деградацию, а не бросает, Писатель идёт по тому же снимку без намерений, а событие `scene_intent` в потоке говорит об этом автору — молчаливая деградация хуже отказа. Замысел хранится колонкой `chapters.scene_intent_json` (миграция 0029), а не таблицей: он живёт одну генерацию и перезаписывается следующей; `NULL` значит «подготовки не было» и отличается от пустого замысла. В промпте Писателя он идёт ПЕРЕД беатами (беат говорит, что происходит, замысел — из чего герой в это идёт) и **не отменяет контракт главы**: где они спорят, сильнее контракт. Там же правила ТЗ 9.3: воплощать намерение действием и речью, а не пересказывать карточку; различать голос повествователя, восприятие POV и прямую речь; не превращать характер в частотное правило (инженер не обязан говорить числами). Проверено живьём на подписке: 27 с, схема прошла, выдуманных номеров событий ноль, намерения участников разные по способу, а не только по словам.

**Критик персонажей (2026-09-20, этап 5, слайс 2):** пятый критик, `critic_character` ([critics/character.ts](packages/agents/src/critics/character.ts)), отвечает на один вопрос — ведут ли себя герои как разные люди. Шесть категорий: `interchangeable`, `out_of_character`, `knowledge_breach`, `relationship_drift`, `flat_voice` и `unusual_but_allowed`. Последняя намеренно не дефект: живой человек иногда поступает против своего описания, и «непривычно» от «невозможно» автор отделяет сам. Границу знаний критик считает **по карточке героя**, а не по канону книги: знание, которого под «Знает» нет, — нарушение, даже если в мире это правда. Взаимозаменяемость требует реплик минимум ДВУХ героев (AC-28) — это держит не только промпт, но и схема (`characterIssueToolSchema.refine`), а одинаковая длина реплик, общая профессия и слова «ладно», «нет» основанием не являются. Каждое замечание несёт цитату, затронутых героев, основание, зачем это в этой сцене, допустимое другое прочтение и что сохранить; поля необязательны в `critiqueIssueSchema` и обязательны в тулсхеме — иначе перестали бы читаться все прежние отчёты четырёх критиков.

Бэкенд — `subscription`, и это **исключение из прежнего правила «все критики на API»**: правила больше нет, бэкенд каждого критика смотреть в `DEFAULT_AGENT_BACKEND`, а не выводить по аналогии с соседом. Следствия приняты: `maxTokens` и `temperature` до модели не доходят, размер держит схема; свой `timeoutMs` 600 с; расход помечается своим бэкендом, а не считается нулевым.

Граф критики перестал предполагать фиксированное число критиков ([graphs/critique.ts](packages/agents/src/graphs/critique.ts)): отчёты копятся списком, узлы и рёбра строятся циклом по `CRITIC_NODES`, порядок в отчёте — порядок этого списка, а не порядок ответов. Прежде агрегация перечисляла четыре именованных поля, и пятый критик добавлялся бы правкой в четырёх местах. Копия списка по умолчанию внутри `runCritique` убрана — он один, `ALL_CRITIC_TYPES`.

**Пропуск — третье состояние.** Критик персонажей не запускается, если в сцене меньше двух названных участников: сравнивать не с кем, вызов впустую. Состав берётся из `assembled.participants` — той же сборки, что дала карточки. Пропущенные уезжают в `skippedCritics` отчёта и печатаются в панели строкой «Не запускались: …»: без неё непроверенное выглядело бы проверенным. Если отсеян весь набор, статус не «done», а ошибка с причиной. Проверено живьём на подписке: 34 с, подброшенное нарушение границы знаний найдено с дословной цитатой и разбором карточки, ложной взаимозаменяемости на двух «не знаю» критик не выдумал.

**Локальная правка (2026-09-20, этап 5, слайс 3):** правка умела одно — «исправь всё серьёзнее такого-то уровня». После критики, которая различает героев, этого мало: на одной главе живого прогона вышло двадцать замечаний, и автор не мог сказать «вот это одно, а вот этот абзац не трогай» (AC-29). Теперь `POST /chapter-versions/:id/repair` принимает `selectedIssueIds` и `protectedFragments`. Идентификатор замечания — `issueIdFor(critic, index)` в [critique.ts](packages/shared/src/critique.ts); своего поля у замечания нет и не заводится: отчёт хранится одним JSON, порядок внутри критика не меняется, а колонка потребовала бы миграции ради того, что и так однозначно. Считают его оба конца — сервер и экран, — поэтому функция одна. **Выбор сильнее фильтра по серьёзности:** автор показал пальцем, и отсекать выбранное порогом значит спорить с ним. Ссылка на замечание, которого в отчёте нет, — 400 с перечислением, а не тихое игнорирование: иначе автор ждёт правку выбранного и получает правку пустого списка.

**Защищённые фрагменты** привязываются по тому же правилу, что доказательство события ([protected-fragments.ts](apps/server/src/utils/protected-fragments.ts)): привязка либо однозначна, либо её нет. Встречающийся дважды отвергается до вызова модели — «защитили не то» хуже, чем «не защитили». Сравнение с поправкой на пробелы и переносы: редактор нормализует документ при загрузке, а правка возвращает прозу с другими переносами, и байт в байт терял бы фрагмент на ровном месте. Предел длины (`MIN_PROTECTED_FRAGMENT_CHARS` = 12) отсекает «Да.» до запроса — короткий кусок всё равно неоднозначен. В промпт Reviser'а они уходят списком с правилом: если замечание требует изменить защищённое, оставить фрагмент и не выполнять замечание. **После правки сервер проверяет, что защищённое дожило** (`survivingFragments`), и потерю называет в потоке `protectedLost` и в логе — но кандидата не отвергает: автор видит текст целиком и вправе счесть замену удачной. Проверено живьём: правка одного выбранного замечания за 96 с, защищённое предложение перенесено дословно, потерь ноль, объём главы почти не изменился (1895 → 1886 слов).

**Проверка различий состава (2026-09-20, этап 5, слайс 4 — этап закрыт):** кнопка «Проверить различия» на этапе персонажей. Агент `cast_check` ([cast-check.ts](packages/agents/src/cast-check.ts), subscription, `timeoutMs` 600 с) сравнивает не прилагательные («оба замкнутые»), а ПЕРВЫЙ ХОД героя в пяти одинаковых положениях — `value_conflict`, `request_for_help`, `mistake`, `pressure_from_authority`, `talk_with_close`. Список закрыт: свободная формулировка превращает отчёт в набор впечатлений, которые не сравнить между парами. Совпадение одной ценности — норма, общая профессия и общий регистр речи книги — не основание; проблема в систематически совпадающих мотивировках, реакциях и речи. У каждой пары обязательны основание, ситуации, **минимум одно направление различения** («похожи» без выхода — замечание, на которое автор ничего не может сделать) и `keep`: сходство бывает замыслом. Требовать максимальной противоположности промпт запрещает прямо — цель различимость, а не контраст.

**Отчёт ничего не меняет и не стареет молча.** Герои правятся только автором; сервер лишь отсеивает пары с номерами вне состава (пара с выдуманным id выбрасывается целиком — «похожи Нина и кто-то» нечитаемо) и кладёт в отчёт `basis` — героев с их ревизиями на момент проверки. `isCastCheckStale` сравнивает его с нынешним составом, и панель пишет «Состав изменился после проверки». Хранение — колонка `books.cast_check_json` (миграция 0030), а не поле в `studio_state`: отчёт описывает утверждённых героев, а не аспекты этапа, и запись через `patchStudioState` наращивала бы ревизию Мастерской — открытая вкладка получала бы 409 на следующей же правке раздела. Проверено живьём: на составе из двух контрастных героев — ноль пар и объяснение, почему они различимы; после добавления почти полного двойника Нины — одна пара, совпадение во всех пяти положениях, три направления и что сохранить.

**Девять находок живого прогона (2026-09-21):** правки про то, что инструмент говорил автору неправду или молчал.

**Расходы Мастерской не считались вовсе.** Четыре аспектных агента (`aspect_playbook`, `aspect_variants`, `aspect_entity_variants`, `aspect_refine`) не имели `onUsage` — шестнадцать вызовов живого прогона и ни одной строки в `llm_usage`. Теперь расход уезжает обратным вызовом, как у Писателя и критиков, и маршрут генерации разделов пишет его под `studio.aspect_variants`. **Подпись бэкенда в подвале** была константой `subscription` — неправда с тех пор, как маршрутизация стала поагентной: критики шли через платный ключ, а подвал говорил про подписку. `GET /api/health` отдаёт `backends` (Писатель и критики, через `resolveBackend`), подвал печатает их по-русски и молчит, когда сервер поля не прислал. **«Ничего не идёт» перестало быть ошибкой:** `GET /books/:id/intake/inflight` и `.../quick-start/inflight` отвечают `200 {running:false}` вместо 404 — опрос раз в две секунды засыпал консоль браузера красным и делал настоящие 404 незаметными; 404 остался за несуществующей книгой. **Негодные данные — 400, а не «HTTP 500: internal_error»:** `app.onError` различает `ZodError` и отдаёт `validation_failed` с деревом причин; испорченный `studio_state` приходил автору сообщением, по которому нельзя понять ни что случилось, ни что делать.

**План книги нельзя было утвердить.** Экран писал «У выбранного варианта нет поглавных строк», и это была правда: `bookOutlineToolSchema` их не требовала, а без них утверждать нечего — автор генерировал план и упирался в тупик. Теперь `chapters` обязателен на выходе планировщика (в хранилище по-прежнему необязателен: старые планы читаются) — тот же приём, что у `architecture` и `contract`. Цена измерена: с поглавным списком ответ перестал укладываться в 600 с (до требования глав — 496 с), поэтому у плана книги свой предел `PLOT_OUTLINE_TIMEOUT_MS` (1200 с) и `maxTokens` 16000, а промпт просит держать строки сжатыми — это оглавление, а не пересказ. **Критики получили `maxTurns: 5`** вместо умолчания в три: на живом прогоне `critic_style` один раз вернул «модель не вызвала инструмент» — так выглядит исчерпание ходов на длинном отчёте.

**Три правки экрана.** Номера глав на доске сюжета были сырым `order_index` (шаг 10), и у третьей главы книги стояло «гл. 30» — `chapterLabels` переводит порядок в позицию, а глава не из книги показывается как `#N`, а не выдуманной позицией. Подпись «Задумка тонкая» появлялась на замысле в 230 символов с героем и конфликтом: текст стал «Можно уточнить», а промпт генератора питчей запрещает вопросы, когда герой И конфликт уже названы. Пакетная генерация «Сгенерировать все оставшиеся» была только на документных этапах — `EntityStageRunner` получил её же: по три категории разом, один `PATCH` на всю пачку (по одному они спорили бы за ревизию этапа), отказ одной категории не уносит остальные.

**Слова и замер (2026-09-21, фаза 6 конвейера):** имена агентов и веток ушли с экрана — «Self-repair» стал «Исправить», «Reviser пишет…» — «Идёт правка…», «Запустить Writer» — «Написать главу», «Outline книги» — «План книги», «План главы (Plot Agent)» — «План главы», «Критика версии» — «Разбор версии». Плитки этапов говорят «Не начат / Черновик / Утверждён»; четвёртое состояние осталось и называется «Не нужен» — это осознанный пропуск лора и предметов, и сливать его с «утверждён» значит врать. Markdown разделов Мастерской рисуется ([Markdown.tsx](apps/web/src/components/Markdown.tsx)): заголовки, списки, абзацы, выделение, своими руками и без библиотеки — подмножество узкое, а готовый разбор markdown приводит к `dangerouslySetInnerHTML` над текстом от модели; правка раздела по-прежнему идёт исходником. Тест-страж [zero-to-chapter.guard.test.tsx](apps/web/src/__tests__/zero-to-chapter.guard.test.tsx) проводит автора по настоящим экранам (полка → замысел → быстрый сбор → план → кабинет) на моках сервера и считает нажатия и вызовы, уходящие в модель: сейчас 7 и 3 при порогах 12 и 4, быстрый режим — 2 нажатия. Мок модуля перечисляет потоковые экспорты поимённо (пространство имён строится копированием собственных свойств, и Proxy отдавал бы `undefined`), а `then` в нём обязан остаться `undefined` — thenable-заглушка подвешивает импорт навсегда. Кабинет рендерится только под data-роутером: `useBlocker` в обычном `MemoryRouter` падает.

**Статус этапа выводится, а не задаётся** ([studio-state.ts](packages/shared/src/studio-state.ts), `deriveStageStatus`): аспект, ждущий решения (`pending`/`generating`/`reviewing`), держит этап в `in_progress`, даже если он необязательный и ничего ещё не принято. `skipped` остаётся только за этапом, все аспекты которого улажены и ни один не принят, — то есть за тем, мимо которого автор действительно прошёл. Необязательные аспекты по-прежнему не мешают этапу закрыться: этап с принятой работой остаётся `complete`. Это существенно для интейка — его черновики приходят необязательными и `reviewing`, а обе страницы этапов на `skipped` рисуют «Этап пропущен» вместо аспектов. Явный пропуск автора `deriveStageStatus` не снимает никогда; снимает его `mergeAspectsIntoStage`, когда на пропущенный этап ложится новый материал.

**Состояние сцены (2026-09-21, идея из vibe_tavern):** карточка героя описывает его вообще, а не сейчас, и физическая обстановка не хранилась нигде — в главе 7 герой в плаще и с рукой на перевязи, в главе 8 плащ исчезал, и поймать это было нечем. Теперь у каждой ВЕРСИИ главы есть анкета непрерывности на её конец: `chapter_scene_states` (миграция 0031), девять жёстких полей — место, время, кто на месте, вид и одежда, что при себе, состояние тела, вокруг, что осталось незакрытым, что изменилось за главу. Ключ — версия, а не глава: переписали текст — у новой версии строки нет, и устаревание берётся отсюда даром, второго механизма свежести не заводили. Схем три, как у профиля V2: чтения (с `.catch` на каждом поле — кривая строка из базы не роняет ни страницу главы, ни сборку контекста), записи (`sceneStateWriteSchema`, для правки автора — там поле не той формы это 400, а не молчаливое умолчание) и ответа модели. Цитат-доказательств у пунктов нет намеренно: анкета не пополняет канон и живёт одну главу.

Считает её агент `scene_state_extractor` ([packages/agents/src/scene-state-extractor.ts](packages/agents/src/scene-state-extractor.ts), subscription, свой `timeoutMs` 600 с) новым видом задания очереди `scene_state`. Вид пришлось заводить пересозданием `memory_jobs`: `CHECK` в SQLite не меняется через `ALTER TABLE` — ровно та причина, по которой на этапе 3 новый вид не заводили вовсе. В `COMMIT_JOB_KINDS` он **не входит**, ставится через `ENQUEUE_JOB_KINDS`: активация фактов, заметок и событий идёт одной транзакцией по готовности всех видов из первого списка, и упавший разбор обстановки не должен задерживать канон главы. Обработчик пишет строку сам — анкета версионно замкнута и от соседних глав не зависит, в отличие от фактов с их интервалами. Авторскую правку (`origin = 'manual'`) запоздавшее задание не затирает; «Пересчитать» снимает строку до постановки задания, потому что пересчёт заказан именно поверх авторской.

В промпт уходит анкета **последней главы до границы сцены** (исключающей, как у событий персонажей) — секция `sceneState`, приоритет 2, не обязательная. Одна, а не список: список растёт с длиной книги и вытесняет поиск со стилем ради сведений, которые к пятнадцатой главе уже неверны. Сборка одна, поэтому анкету видят Писатель, все пять критиков и правка; у критика канона это ещё один способ поймать расхождение. Вся SQL границы — в [utils/scene-state.ts](apps/server/src/utils/scene-state.ts), второй экземпляр выбора «последняя глава до границы» разошёлся бы молча. Экран — `SceneStatePanel` в правой колонке главы; правка ведётся сырым текстом и разбирается один раз при сохранении: разбор на каждое нажатие стирал пробел прямо под курсором. **Перенос правки на новую версию:** перезапись главы заводит новую версию, и авторская анкета остаётся у прежней. `GET /chapters/:id/scene-state` отдаёт её полем `carry` ([`loadCarryableSceneState`](apps/server/src/utils/scene-state.ts)), панель предлагает перенести кнопкой, перенос идёт обычным `PATCH` — своего маршрута нет. Автоматического переноса нет намеренно: анкета описывает конец главы, а текст главы как раз переписан, и подставленная без спроса правка стала бы описанием заменённого текста. Предлагать нечего, когда правка пуста, когда автор уже правил текущую версию (его решение новее) и когда правок не было; берётся самая поздняя авторская строка. Спецификация: `docs/superpowers/specs/2026-09-21-scene-state-design.md`.

**Заимствования из litrab.ai (2026-09-21):** восемь приёмов конкурента, спецификация `docs/superpowers/specs/2026-09-21-litrab-borrowings.md`, одна миграция 0032 на все восемь. Другие имена героя — экран над `entity_aliases` (`AliasEditor`); API и резолвер были готовы ещё с ADR 0003, экрана не было — доля вины за то, что события героини «Нины/Агаты» отвергались все до одного. `books.author_notes` — единственное поле книги, которое НЕ читает ни одна сборка контекста; инвариант закреплён тестом на маячок в `litrab-borrowings.test.ts` (и в `assembleGenerationContext`, и в `studioContextToPrompt(loadStudioContext(...))`) — заводить читателя нельзя. [`AuthorNotesPanel`](apps/web/src/components/chapter/AuthorNotesPanel.tsx) получила ту же защиту, что уже стояла на замысле в `ConceptStage`: книга догружается позже первого рендера страницы главы (`initialNotes` идёт `null`, затем настоящими заметками), и безусловный резинк стирал бы набранное тем же путём — правка держит `useRef` последнего известного значения пропа и переписывает `text`, только если автор его не трогал, плюс `flushNow` по `blur` и при размонтировании: уход со страницы раньше паузы автосохранения тоже не должен терять текст. «Глазок» `characters.hidden_from_prompts` фильтруется ровно в одном месте — `gatherCharacterContext`; POV из плана (`alwaysIncludeIds`) фильтр обходит, планировщик (`loadCanonCast`), `cast_check` и резолвер фактов видят весь состав — факт о скрытом герое всё равно принадлежит ему. Ревизию карточки флаг не двигает: это не правка профиля, истории у него нет. Inline «Описать» (`describe` + `sense`) вплетает одну деталь одного канала и намеренно не видит текст ПОСЛЕ фрагмента — иначе модель продолжает сцену вместо того, чтобы насытить написанное; де-AI правило про сенсорную плотность держится тем же, чем и раньше — деталь одна, а не три.

Отчёт о потерях после правки живёт в `ProposalPanel`: дельта объёма (порог 10%, только для `repair`), `protectedLost` с сервера (раньше терялся — панель его не читала), `findLostMentions` по убранным или заменённым абзацам через `mentionsEntityName` (с поправкой на падежи, без `lower()`/`\b`). Свежесть стиля: `GET /books/:id/style-freshness`, порог три главы после `last_extracted_at`, блендам не считается (у них нет своего корпуса); добор глав кладёт корпус через [`insertReferenceCorpus`](apps/server/src/utils/style-corpus.ts) (общий хелпер и для загрузки корпуса, и для добора) и НЕ удаляет старые корпуса, извлечение — прежним маршрутом со стороны клиента, вторым шагом. Чат (`book_chat`, subscription, модель `plotModel` книги — разговор, не проза) — тонкий потребитель `assembleGenerationContext`; в `contextBlocks` уходит паспорт стиля (`assembled.styleContext.prompt` — без него правило «в голосе книги» не на чем держится), но не образцы речи (`styleFewShot: 0` — разговору не нужно копировать чужие фразы) и не дословный хвост предыдущей главы (`previousTail` — глава и так подана целиком, хвост поверх нёс бы только цену бюджета). Треды привязаны к главе и друг о друге не знают, в главу не пишут; `#`-упоминаний других глав нет — потолок.

Глава по беатам: `mode: "beats"` в `POST /chapters/:id/write`, один вызов на беат при той же стабильной части промпта (кэш-префикс цел), кандидат дописывается после каждого беата (`appendProposalProgress`) — падение процесса не теряет написанное. `hold` ≠ `cancel`: дописывает текущий беат и сохраняет кандидата `incomplete` со `stopReason: "held"`, текст остаётся принимаемым. «Дописать с беата k» берёт префикс из принятой версии через `content_json`/`docToBlocks(...).join("\n\n")`, а не через `content_text` — тот пишется `extractText`'ом (`parts.join(" ")`) и склеил бы абзацы принятой версии в одну строку, необратимо стирая разбивку автора при принятии дописанного кандидата. Потолок остаётся: `docToBlocks` отдаёт текст ЛЮБОГО верхнеуровневого узла как обычный абзац, так что заголовки, цитаты и пункты списка возвращаются абзацами, а начертания теряются. Обрыв прогона тоже пересмотрен: беат-прогон, упавший с уже написанными беатами, завершается `incomplete`/`interrupted` и остаётся принимаемым — и в `catch` самого маршрута, и в стартовой чистке зависших `streaming`-строк (`critique-recovery.ts`); целая глава без единого беата и прогон без единого написанного беата по-прежнему падают в `failed`. С какого беата продолжать, экран узнаёт по последнему принятому кандидату главы (`beatsDone < beatsTotal`), не заводя новой колонки у версии. `prosePlainTextToProseMirror` переехал в [`utils/prosemirror.ts`](apps/server/src/utils/prosemirror.ts) из двух копий (`plot.ts`, `critique.ts`).

At the start of a task:

1. Call `recall` вЂ” durable lessons scoped to this repo, most specific first. Call it
   with no query to see everything in scope; that is usually what you want first.
2. Read `projects/<this-repo>/README.md` through `search` or the `vault://` resource.
   It is the single source of this project's current status and next step.
3. If `recall` and `search` return the notes but not the answer вЂ” several notes bear
   on the question and they disagree, or the judgement spans them вЂ” use `reason`.

At a meaningful stopping point, before the context is lost:

4. Call `record_work`. Fill `changes`, `decisions`, `learned`, `verification` and
   `open`. A future session cannot reconstruct these from the diff, and a sparse
   record is near-worthless six weeks later, which is when it gets read.
5. If something you learned would still be true in a **different** repository, call
   `remember`. That is the test. A log of what you did today is `record_work`, not a
   memory вЂ” a memory store filling with status updates is worse than an empty one.
6. Say so if the status note is now out of date. It is the file that answers "where
   did we stop", and it is only worth reading if it is current.

If something you expect to be in the vault cannot be found, call `health` before
concluding it is not there. Every failure in this layer вЂ” a missing index, a
misconfigured root, an unresolved caller identity вЂ” presents identically as "no
results", and `health` is what distinguishes them.

Never write vault paths, vault contents, or session URLs into commits, PR
descriptions, or code comments in this repository.
